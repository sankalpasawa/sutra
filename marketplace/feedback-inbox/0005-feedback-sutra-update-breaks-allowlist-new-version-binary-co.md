# #5 [Feedback] Sutra update breaks allowlist — new version binary + common tools prompt for permission every session

**Author:** vinitharmalkar  |  **State:** OPEN  |  **Labels:** —
**Created:** 2026-04-27T13:53:05Z  |  **Updated:** 2026-04-28T13:59:52Z
**URL:** https://github.com/sankalpasawa/sutra/issues/5

---

## Problem

Every time Sutra updates to a new version, the user faces a fresh wave of permission prompts — because the **new binary path is not in the allowlist**, and **common tools that Sutra's own governance hooks rely on are never auto-added**. The allowlist has grown to 80+ hardcoded entries through piecemeal approvals across sessions, yet still misses fundamental read-only commands.

This is a friction tax paid on every update. The user should not have to manually approve the same class of tools again every time Sutra bumps a version number.

---

## Permissions triggered in today's session (2026-04-27, after Sutra 1.12.0 → 2.4.0 update)

### 1. Sutra binary — version path not in allowlist
**Triggered by:** `/core:start` running `sutra start`

The allowlist currently contains:
```
Bash(/Users/vinit/.claude/plugins/cache/sutra/core/1.9.4/bin/sutra start *)
Bash(/Users/vinit/.claude/plugins/cache/sutra/core/1.9.4/bin/sutra update *)
Bash(/Users/vinit/.claude/plugins/cache/sutra/core/1.9.4/bin/sutra status *)
Bash(/Users/vinit/.claude/plugins/cache/sutra/core/1.12.0/bin/sutra start *)
Bash(/Users/vinit/.claude/plugins/cache/sutra/core/1.12.0/bin/sutra update *)
```

After the update to 2.4.0, **none of these match**. The new binary at:
```
/Users/vinit/.claude/plugins/cache/sutra/core/2.4.0/bin/sutra start
```
…prompted for permission even though the user has approved this exact command structure for every previous version.

**Root cause:** `sutra update` does not write the new version's binary path to the Claude Code allowlist. The user must manually approve it (or run the `/core:permissions` paste-ready snippet) every single update.

## Pattern: allowlist grows by piecemeal approval, never by Sutra intent

The current `settings.local.json` has **80+ allowlist entries** accumulated over many sessions. Yet each new session still hits permission walls on:
- The new Sutra binary version (every update)
- Basic UNIX read-only tools (`find`, `jq`, `head`, `wc`)
- `gh issue *` (used for Sutra feedback filing)

This happens because the allowlist is **reactive** (user approves when prompted) rather than **proactive** (Sutra declares what it needs and installs those permissions on setup).

## Requested Changes

### Fix 1 — `sutra update` / `sutra start` must patch the allowlist automatically
When Sutra installs or updates to a new version, it should write the new binary's allowlist entries to `settings.local.json` before the user ever needs to run a command. The version-specific path should be added automatically, and old versions can be left (they're harmless) or pruned.

**Proposed entries to auto-add on update:**
```json
"Bash(/Users/vinit/.claude/plugins/cache/sutra/core/X.Y.Z/bin/sutra *)"
```
The `/core:permissions` output already generates this snippet — it just isn't applied automatically.

### Fix 2 — Sutra's baseline allowlist should include the read-only UNIX tools its own governance uses
Sutra's subagent guidance explicitly instructs agents to use `jq`, `find`, `head`, and `wc` for file probing. These tools should be in Sutra's **declared permission manifest** and added to the allowlist at install time:

```json
"Bash(find *)",
"Bash(jq *)",
"Bash(head *)",
"Bash(wc *)",
"Bash(cat *)"
```
These are all read-only. There is no security case for prompting on them.

### Fix 3 — Add `gh issue *` to the Sutra feedback workflow allowlist
The `/core:feedback` skill and the Sutra feedback filing workflow both result in `gh issue create` calls. This should be in the declared allowlist:
```json
"Bash(gh issue *)"
```

### Fix 4 — Replace session-specific hardcoded jq path with a glob
The current stale entry:
```
Bash(jq -r '.fileContent' "/Users/vinit/.claude/projects/-Users-vinit/a5cfb880-.../...")
```
Should be replaced with:
```
"Bash(jq *)"
```
This will match all jq invocations without requiring path-specific approvals.
