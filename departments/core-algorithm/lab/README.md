# Experimental reference — one kernel, 49 extension cases

**Build label:** `sutra-kernel-extensions/0.16.0-ordered`. This is an independent study; do not treat it as a released implementation of production Sutra Core or J2/Native. 0.16.0-ordered (Core Algorithm program; built 2026-11-13, laid on the add-on base 2026-11-14) adds three matrix rows about order and evidence before an act, as files only: packs 120 to 129, cases 54 to 56, one recorded sequence (`scenes.ordered`: sixteen lives, each one State taken through named steps with a snapshot after every step; forty looks and forty-eight runs, the numbers its scene file states as `LOOKS` and `RUNS` and a unit test counts again in the record), one action kind (`kinds/scrub_text.py`), three extensions outside the kernel, unit tests (`tests/test_ordered.py`) and checks S70 to S79. The kernel is unchanged, byte for byte, and so are the cases, the event record and the ask record the lab held before. Two things it held before move, as a declared kind moves them: the record's list of handlers gains `scrub_text` (the kind file, by sha256) beside the entries it had, which stay as they were, and the three implementation lenses, which name every registered kind, now name it too; every other lens, the reflection summary among them, is as it was. How the record is checked: S70 to S78 hold their own script of every life and their own bookkeeper; from the pack files and the script they rebuild every row handed in, every stamp, every receipt (its hash included), the fields of every run (what it needs and its proof among them, which the base verifier does not read), every snapshot and the derived state and views of the three cases, and compare each whole, as JSON text. One field of a run is not rebuilt: the count of options (`pareto_options`) is held to the run's own SELECT line, because the checks plan nothing. A trace is read line by line, for what each line must say: its first line (the goal and its scope) and its last (the status, the work state, the run's root); every RETAIN, REFINE, METHOD_MATCH, METHOD_ABSENT, QUERY_EVIDENCE, REFUSED and ADMISSION line of the search, whole, against the books as they stood; the steps and the full cost on the one SELECT line, or the one BLOCK line, whole; after the SELECT line that every line is of a kind that belongs there (a gate, an effect, a stop, a closed question, the end), the gate lines whole and in their order, and the receipt on each effect line, in order; every STEP_STOPPED and ASK_CLOSED line, whole; the rows that the METHOD_ABSENT, QUERY_EVIDENCE and REFUSED lines name between them; in the lives whose script lists them, every gate line of the trace in its order; and the trace's hash chain. Known limits of this version. First, a fault of the sanitizer, stated and pinned here and not repaired (the repair is new code: the first thing owed to the next version): an e-mail address written straight after another one, with nothing between the two but characters an address may hold, can be left in the text the scrub calls clean: so it is in `anna@example.org-ben@example.org`, and when the two are joined by `+`, by `_`, by a digit or by `%2C` (a list of addresses in a URL). The e-mail detector of `extensions/ordered_effects.py` begins a match only where the character before is not one an address may hold (a look-behind, put there after the first review so that a long text is read once), so after one address it cannot begin another until a character of some other kind has come: in those texts the scrub counts one redaction, and the State writes and sends the text, second address and all, as scrubbed. The sentence in that file which says that the look-behind leaves what is matched unchanged is wrong, and is corrected with the repair. The deployed pattern has no look-behind and redacts both addresses, and so does the check module's own copy of the sanitizer: the two readings of one scrub disagree on such words, so an honest life recorded with them would fail this version's own checks at that step (the recorded words hold no such pair). The unit test `test_known_limit_an_address_joined_to_the_one_before_it_stays_in_the_text_called_clean` shows both halves, the State that sends the address, and the honest life the checks refuse. Second, what of a trace rests on its hash chain alone, so that a record rewritten there, chained again and (the sequence) sealed again can pass every check: the order and the number of the lines of a search, beyond what is held above (a line taken out, doubled or moved); one more TERMINAL or GOAL_ACCEPTED line in the search; a key added to a row of a trace, or to what a SELECT or an effect line says; the count of options, when the run's field and its SELECT line are forged together; and the order of the gate and effect lines after the plan is chosen. No status, step, receipt, snapshot or stored row can be forged this way: those are rebuilt from the pack files and the script and compared whole. The unit test `test_known_limit_what_of_a_trace_rests_on_the_chain_alone` makes one record forged in every one of these places, shows every check passing on it and the same kind of change refused where the checks do read, and shows S79 failing on another such record for a reason of its own (one of its hand-made forgeries rewrites the very line that was taken out, and a forgery that cannot be made counts as not caught). The check module's own opening words still say that only the order and the number of the lines of a search rest on the chain: they understate it, and they change with its code in the next version. ### Structure

- `kernel/core.py`: bounded recursive resolver and safe local action boundary; since 0.4.0 it carries no learning, since 0.7.0 only the `simulate_fact` effect and a registry for the rest.
- `extensions/asks.py`: the `ask` action kind with its hooks, `answer` (the stamp) and `open_asks` (since 0.8.0).
- `extensions/constructor.py`: the `compile_candidate` and `emit_artifact` action handlers (out of the kernel since 0.7.0).
- `scenarios/`: authored, reviewed-in-fixture JSON packs.
- `extensions/knowledge.py`, `reflection.py` (with `Learner`, the per-run candidate-only learning since 0.4.0), `j2_projection.py`: bounded proposal utilities, **not** true external data/model/J2 integration.
- `extensions/standards.py`: the evidence adapter: a checklist over a workflow JSON becomes verified evidence rows (source = the adapter, version = the digest of what was checked); it runs when packs are authored, never inside the kernel.
- `extensions/implementation.py`: the implementation generator: from a plan and its state, a workflow in the `sutra-native` user-kit shape, its atoms, the owning department's scaffold and a page; PROPOSED_ONLY, deterministic, writes nothing, runs nothing.
- `tools/`: fixture, run and static-viewer scripts.
- `qa/`: independent verifier (does not import kernel), optional browser tests.
- `tests/`: regression and negative tests.
- `cases/`, `tools/packs/`, `tools/scenes/`, `kinds/`, `qa/checks/` and what later versions put into `extensions/` and `tests/`: the files of versions that only add; `added.json` is the book of them (every file by sha256) and of what the lab had recorded before (see "Additive versions" above).
- `release/baseline_v0_1_core.py`: historic experimental v0.1 reference fixture used by unit/trace verifier, not frozen historical Sutra Core v0.2.2.

### Do not claim

This test uses toy resource units, human-authored domain rules, simulated effect receipts and seeded candidate components. It does not move inventory, send a message, deploy an app, generate unknown code independently or allow itself to approve any release.
