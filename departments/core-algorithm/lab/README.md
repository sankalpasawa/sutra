# Experimental reference — one kernel, 63 extension cases

**Build label:** `sutra-kernel-extensions/0.20.0-learn`. This is an independent study; do not treat it as a released implementation of production Sutra Core or J2/Native. 0.20.0-learn (Core Algorithm program, 2026-11-15) adds to the learn feature a reading of what an independent judge found it did not learn from the program's own records, as new files only: one extension (`extensions/learn.py`), five packs, three cases (160 to 162), three recorded sequences (`learn_checks`, `learn_across`, `learn_settled`) and their unit tests (`tests/test_learn.py`). It brings no action kind and no check module, and the kernel is unchanged. What earlier versions recorded stays as it was: the add-on base's check S202 holds every pinned record to its pin. Why it was made. The owner ran a goal of his through the algorithm (a UI built by one agent, five examples solved through it by five users, each judged by a judge, every agent running its own work through the algorithm too); the learn feature as it stood (the reader of 0.19.0 and the Learner) then read every kept record, and an independent judge listed what two or more independent sources found that it did not learn, each finding with the rows that hold it (`.tmp/core-algo-learning/judge/FINDINGS.json`). This version meets the judge's statement 4 and parts of statements 1, 3 and 6, as three needs, and no other: N1 every check row with the checker's own words (statements 1, in part, and 4; findings F03, F04, F31, and F10 in part); N2 more than one record at a time (statement 3, in part: a block, a stopped step, a failed check, a pack and a stated row seen in several records are one thing each, and a question only as an answer, with its party and its truth, L16; F01, F06, F18, F30); N3 who stated a fact, against what the plan says (part of statement 6; F14). It was made under ruling R35: each need was first handed to the parts the lab had, on records with the data's shape; what they made of it is recorded under `existing_parts` in the three sequences (held by the tests of the class `Sequences`) and held on desks of the tests by the class `Existing`. The reader says nothing of a check row (it reads what ran, what was asked and what was decided; a hand-over that goes out again is a waiting run), one Learner fed every run says nothing of a waiting run, and `reflect` proposes nothing (`test_the_reader_the_learner_and_reflect_say_nothing_of_the_check_rows`). The record adapter's ledger holds a row with its fact, truth, source and version only: not the checker's words (`why`) and not the receipt it checks (`checks`) (`test_the_ledger_holds_a_check_row_without_the_checkers_words_or_the_receipt_it_checks`). The record adapter's `counts()` counts the runs of a goal by status word in one record and cites each (`test_the_record_adapters_counts_count_runs_of_a_goal_by_status_word_in_one_record`): not runs in a row, and not across records. The reader refuses mornings of one desk handed in as one record, in the record adapter's words, because they do not continue one another (two in `test_the_reader_refuses_records_that_do_not_continue_one_another`, the three of `learn_across` in `test_across_what_the_parts_the_lab_had_say_of_the_same_records`), and on each record alone it says nothing of a blocked run; one Learner fed every run of several records says one gap a blocked run, none for a no (L14), and names no record, no entry and no count (`test_one_learner_fed_every_run_of_two_records_says_one_gap_a_blocked_run_and_names_no_entry`). At run time the hand-over kind holds a check row to its try and the ask's stamp holds an answer to its question; nothing the lab had reads kept rows against the plan. So one part is added, and it only reads: `extensions/learn.py`. The case that failed without it is each of the three sequences, whose `existing_parts` hold the rows and the counts, and not the checker's words, the receipt a row checks, the plan beside the rows, runs of a goal in a row, or one thing across records. What it is. `learn.proposals(records, least)` takes a list of records, each a list of one or more (text, head) as the record adapter takes it (one journal, or a chain of journals read as one), and the number of times that make a repeat (also the number of records in which a thing must stand), and gives proposals: plain data, each with the record it comes from (named by its first journal), or for a thing of several records `records` and `record_ids`, with `support`, the rows it rests on (`at`: journal, entry number, entry hash, for a row of a pack its place in the pack's evidence, for a run its run id) and the status `PROPOSED_ONLY`. It reads the rows handed to the State at the journal's event door and in the evidence of packs, each with its source (a kept row of a pack that names no source refuses the call, L15); an answer is read as an answer. A row is read in its own scope, else in the State's: the scope the last pack of the record named, else the scope a new State starts in (`learn.FIRST_SCOPE`, held equal to the kernel's by `test_c1_a_desk_whose_packs_name_no_scope_is_read_in_the_scope_a_new_state_starts_in`); a row after the desk's pack and before any run is read in the pack's scope (`test_c1_a_row_after_the_desks_pack_and_before_any_run_is_read_in_the_scope_the_pack_names`). Only a pack moves the State's scope, so every run of a record is run in the scope the learn feature holds, as 200 random histories show (`test_c1_in_random_histories_of_a_desk_the_check_rows_are_the_rows_the_kind_reads`). Per record, in the order the records are given: the check rows and the stated rows in the order the State was handed them (entry by entry, the rows of a pack in their order), then the repeats in the order of their first row (journal of the chain, then entry); then the things of several records in the order they were first seen (`test_c1_in_a_chain_the_plan_and_the_order_of_the_repeats_run_across_the_journals`). The claims, each with unit tests in `tests/test_learn.py` named `test_cN_...` or named here; every clause not tied to a sequence is held by unit tests alone, since this version brings no check module (L7). a plan is admitted and priced at its full cost, also for steps that will be skipped at their turn, so a goal can stop as `RESOURCE_REQUIRED` for a budget it would not use; a constructor spec is not shape-checked when its pack is applied, so a malformed one stops the run at that step; amounts are bounded one by one (an integer of at most 4300 digits) but their sums are not, so a plan whose costs add up to more digits cannot be written down on a Python that limits the text of an integer; the flag `execute` is read as it is given, more than once in a run, so it must be exactly true or false; a version named inside `depends_on` is not checked, so a dependency on a version that is true, a list or an object is stored and can never be valid (0.9.0 removed these three: see its passage above); ### Structure

- `kernel/core.py`: bounded recursive resolver and safe local action boundary; since 0.4.0 it carries no learning, since 0.7.0 only the `simulate_fact` effect and a registry for the rest.
- `extensions/asks.py`: the `ask` action kind with its hooks, `answer` (the stamp) and `open_asks` (since 0.8.0).
- `extensions/constructor.py`: the `compile_candidate` and `emit_artifact` action handlers (out of the kernel since 0.7.0).
- `scenarios/`: authored, reviewed-in-fixture JSON packs.
- `extensions/knowledge.py`, `reflection.py` (with `Learner`, the per-run candidate-only learning since 0.4.0), `j2_projection.py`: bounded proposal utilities, **not** true external data/model/J2 integration.
- `extensions/standards.py`: the evidence adapter: a checklist over a workflow JSON becomes verified evidence rows (source = the adapter, version = the digest of what was checked); it runs when packs are authored, never inside the kernel.
- `extensions/implementation.py`: the implementation generator: from a plan and its state, a workflow in the `sutra-native` user-kit shape, its atoms, the owning department's scaffold and a page; PROPOSED_ONLY, deterministic, writes nothing, runs nothing.
- `tools/`: fixture, run and static-viewer scripts.
- `qa/`: independent verifier (does not import kernel), optional browser tests.
- `tests/`: regression and negative tests.
- `cases/`, `tools/packs/`, `tools/scenes/`, `kinds/`, `qa/checks/` and what later versions put into `extensions/` and `tests/`: the files of versions that only add; `added.json` is the book of them (every file by sha256) and of what the lab had recorded before (see "Additive versions" above).
- `release/baseline_v0_1_core.py`: historic experimental v0.1 reference fixture used by unit/trace verifier, not frozen historical Sutra Core v0.2.2.
