# Experimental reference — one kernel, 30 extension cases

**Build label:** `sutra-kernel-extensions/0.8.0-ask`. This is an independent study; do not treat it as a released implementation of production Sutra Core or J2/Native. 0.8.0 (Core Algorithm program, 2026-11-11) lets a step ask a person and wait, and tightens what the kernel accepts. The kernel has no word of asking; it gains generic things, each with a counterexample test (the tests do not yet kill every mutation of the code): (1) an action kind may carry hooks, reviewed code like its handler (`check` when a pack is applied, `plan` while planning, `settle` at the end of an executed run), so a kind keeps its own books; the registry's shape changed with it (`ACTIONS[kind]` is a dict holding `run` and the hooks); (2) a plan may wait on a pending step (the wait needs none of that step's prerequisites and competes by the same preference rule; if it wins nothing runs), and a step may park, after which nothing runs and only what ran is reported (status `WAITING` in both cases); (3) evidence may be a decision: `final` true on a TRUE or FALSE row that rests on nothing else; a FALSE decision blocks its fact as `REFUSED` before any rule or method, and a decision stands until another decision replaces it (a row turned away is journalled as `DECISION_STANDS`); (4) a pack applies whole or not at all, every refusal is a `ValueError`, and what is handed in (a pack, a row, an event, a receipt) is first rebuilt as plain JSON data by exact type, without calling any code of what is handed in (types are compared by identity; a dict is read once, as one snapshot of its pairs, and a list item by item; at most 16 levels below the top object, 18 for a pack, and 100000 items in all, keys and containers counted; an integer has at most 4300 digits), so the State keeps its own copy and a crafted object, a tuple, a number used as a key, NaN, an infinity or text that is not UTF-8 is refused; a version is a name, a number or null and compares as JSON text (1 and 1.0 are two versions; null and no version are one), a goal is a name; amounts are whole non-negative numbers (5.0 is refused where 5 is meant); a method needs an id, an effect, a grant and a provider, may require at most 10000 facts (so the row its step writes stays inside the door's bound) and may only cost what the budget has; a pack's goals, grants, rules, evidence rows and scope are shape-checked, `verified`, `final` and `approved` are exactly true or false (null is refused, in an event as in a pack), and a hook the kernel does not know is refused; (5) a step whose effect already reads TRUE when its turn comes is skipped, neither run nor paid, and the record says so: one `STEP_ALREADY_TRUE` line in the run's hash chain and the step under `skipped` in the result (the row that came back stands with its own source, version and dependencies; a kind whose product is not its effect fact, such as `compile_candidate`, is skipped the same way); and what the kernel hands out (a fact, a result's provenance and candidates) is a copy, so a stored row changes only through `observe`. The asking lives in `extensions/asks.py`: a question is out from the receipt the kernel issued until a decision is on its fact (the stamp, or a final row from any channel); no other evidence closes it: a verified TRUE row lets the plan go on without the answer, and when that row goes the plan waits on the same question again; a late yes on a fact that such a row already made true keeps the row's version, so nothing made on it is undone or paid twice (when that row was withdrawn before the yes came, the yes is a new decision with its own version, and what rested on the row is made and paid again); so there is one question per fact and scope, asked once and paid once; the stamp (`answer`) must present the receipt that is on the books, in scope, from the asked party, and the books keep that receipt, so a question can always be answered from `open_asks`. Case 29 and the `ask_events` record show it. Adversarial rounds on the design and on every build shaped it, and the later builds made it smaller: answers no longer rest on "grounds", questions are never withdrawn, and a wait no longer depends on what the question was asked on, because that bookkeeping kept failing. The fifth round cut one more rule: a question used to be closed by any verified TRUE row as well, so a row that came back closed a question just asked and the asked party's answer was refused. The sixth round showed that comparing the rebuilt copy with what was handed in ran the caller's own code on that copy; the door now reads by exact type and runs none. The seventh round showed that the door still asked a class's metaclass whether it was a number (`in` compares with ==), that it read a dict twice, so the caller's own garbage, collected in between, could rewrite it, and that the row a step writes could be refused by the bound meant for callers; types are now compared by identity, a dict is read once, and a method may require at most 10000 facts. The eighth round refuted nothing. It showed that a snapshot of a list, added with the seventh round's fixes, was not one read on Python before 3.12, so a list is read item by item again, as in the build before; the other points it raised are stated below as limits. What the door cannot guard is code the caller left to run by itself (a finalizer of its garbage, another thread): it can change a container before the door reads it, and code that reaches into the kernel's own frames or fields can change anything, as any code in the same process can; short of that, what the door stores is checked and is the State's own. The generator, the Learner, the graph diff and the J2 view read the whole plan of a run (what ran, what was skipped, what is waited on, what is still to run) through one function, in the selection's order. Every step of a generated workflow has its own id (two methods whose names give one slug get a suffix), a step waits for the first earlier step that makes each of its needs, with one edge per maker, step and fact, a question that was already out is listed first and waits for nothing, and a workflow in which two steps share an id is refused. The independent verifier compares every recorded run with its trace, with the packs it says it loaded and with the kernel's claim sentence; the comment above its check S42 lists what it does not check. The kernel went from 319 to 373 lines. What changed in the record: on the same packs the kernel gives the same status, actions, receipts and trace roots for all 29 older cases, and 28 of them keep their trace root in this lab; case 27 does not, because the generator now writes a `kind` on every method step and counts every step of the workflow in its last step's line, which changes the digest pack 64 carries as its evidence version. Known limits: a decision does not lapse when what the question was asked on changes; a question cannot be withdrawn or put to someone else: it ends only by a decision, so one that nobody answers stays on the books for good, and an answer that arrives late, also after other evidence let the plan go on, is still a decision on the fact (a late no undoes what was made on that evidence); a plan is admitted and priced at its full cost, also for steps that will be skipped at their turn, so a goal can stop as `RESOURCE_REQUIRED` for a budget it would not use; a constructor spec is not shape-checked when its pack is applied, so a malformed one stops the run at that step; `apply` copies the whole State for its trial, so its cost grows with the journal, and the State's fields are new objects after every `apply`; a generated workflow words every step the owner approves with the runtime's word ("the owner stamps the ask"), next to steps of kind `ask`; waiting costs nothing and never expires, so a wait can hold back a dearer plan that is ready; a goal that waits runs none of its other pending steps; a rule for a fact shadows every method for it, asks included; the gate reads stored evidence only, so a plan whose step needs a condition that holds only through a rule, or one made by a kind that writes no evidence (`compile_candidate`), is still offered and then stops at the gate (unchanged from 0.7.0); a handler, a hook or the gate that raises in the middle of a plan ends the run without a record, and the steps before it stay done and paid; in a call that runs several goals (`run_standing`, `on_event`, `answer`) the results of the goals already run are lost with it, though a question they asked stays on the books (the step-outcome version turns this into a recorded stop); a question's books are settled only by executed runs in its scope, never by a dry look; simulated effects still carry one constant version, so an effect made on a prerequisite reads valid again when that prerequisite is made again (unchanged from 0.7.0); two States with the same packs and the same journal issue the same receipt; amounts are bounded one by one (an integer of at most 4300 digits) but their sums are not, so a plan whose costs add up to more digits cannot be written down on a Python that limits the text of an integer; the flag `execute` is read as it is given, more than once in a run, so it must be exactly true or false; a version named inside `depends_on` is not checked, so a dependency on a version that is true, a list or an object is stored and can never be valid (the next version removes these three); chains hundreds of rows long exhaust Python's recursion in `fact` and `on_event` (unchanged). 0.7.0 was the second shrink version (move-outs M2 and M3): the kernel gets one generic primitive, an action-handler registry, keeps the gate (re-admission, prerequisites true, cost, provider slot, the receipt's own fields, the log) and gives up the effect; `compile_candidate` and `emit_artifact` leave `kernel/core.py` for `extensions/constructor.py` with byte-identical receipts and trace roots on cases 04, 15, 16 and an artifact fixture. A State keeps the registry as it stood when it was built; packs can never add a kind. 0.6.0 (kernel unchanged from 0.4.0) makes the implementation generator emit each step's prerequisites (`after`) and the plan's dependency edges, refuse a workflow whose step comes before its prerequisite, and adds a fourth domain, a website (plan, write, build, check), as case 28. 0.5.0 was a pack-only version (Core Algorithm program slice S3, 2026-11-10; kernel unchanged from 0.4.0): a standard becomes an ordinary approved rule (`R-REGISTRABLE@1`), its facts come from an evidence adapter over a workflow JSON (`extensions/standards.py`), and cases 25 to 27 record a hand-written workflow failing the standard, a reviewed method repairing it, and a generated workflow passing on evidence alone. 0.4.0 was the first shrink version (Core Algorithm program rule R2, move-out M1, 2026-11-10): the learning block and its `learned_signatures` memory left `kernel/core.py` (341 to 323 lines) for `extensions/reflection.py` (`Learner`), with a counterexample test that fails on 0.3.0 and an equivalence test on the recorded learning cases. 0.3.0 added the proposal-only implementation generator (`extensions/implementation.py`, program rung L1); the kernel was unchanged from 0.2.0 until 0.4.0.

Requirements: Python 3.10+ standard library. From **this `lab/` directory**:

Expected results with the included authored fixture packs: 30 deterministic recorded cases, 103 passing unit tests and 48 independent local checks (0.7.0 had 29 cases, 75 and 41; 0.6.0 had 70 and 39; 0.5.0 had 28 cases, 67 and 37; 0.4.0 had 25 cases, 62 and 36; 0.3.0 had 57 and 33, 0.2.0 had 54 and 31; the five tests and three checks added in 0.4.0 cover the move-out of learning, those of 0.3.0 the implementation generator). What changed in the record with 0.4.0: the trace of a learning case no longer carries a `LEARN_CANDIDATE` event, so the trace roots of cases 05 to 08 differ from 0.3.0 and case 05 now shares its root with case 04; each learning list is bound to its run by `learning_record` (trace root + sha256 of the list), which check S36 verifies. `qa/independent_verify.py` **does not import** the resolver and rejects a deliberately altered event chain, but verifies synthetic consistency only. `tools/build_viewer.py` and `qa/browser_test.py` optionally render/check the offline viewer with Playwright and Chromium installed; the earlier archive recorded 21 browser assertions, not rerun for this publication.

`results/` and `site/` are generated locally, not authoritative external observations. Source integrity of the historical experiment was checked before importing here; commits to this department create new repository object hashes, not a retroactive Core v0.2.2 release.

### Structure

- `kernel/core.py`: bounded recursive resolver and safe local action boundary; since 0.4.0 it carries no learning, since 0.7.0 only the `simulate_fact` effect and a registry for the rest.
- `extensions/asks.py`: the `ask` action kind with its hooks, `answer` (the stamp) and `open_asks` (since 0.8.0).
- `extensions/constructor.py`: the `compile_candidate` and `emit_artifact` action handlers (out of the kernel since 0.7.0).
- `scenarios/`: authored, reviewed-in-fixture JSON packs.
- `extensions/knowledge.py`, `reflection.py` (with `Learner`, the per-run candidate-only learning since 0.4.0), `j2_projection.py`: bounded proposal utilities, **not** true external data/model/J2 integration.
- `extensions/standards.py`: the evidence adapter: a checklist over a workflow JSON becomes verified evidence rows (source = the adapter, version = the digest of what was checked); it runs when packs are authored, never inside the kernel.
- `extensions/implementation.py`: the implementation generator: from a plan and its state, a workflow in the `sutra-native` user-kit shape, its atoms, the owning department's scaffold and a page; PROPOSED_ONLY, deterministic, writes nothing, runs nothing.
- `tools/`: fixture, run and static-viewer scripts.
- `qa/`: independent verifier (does not import kernel), optional browser tests.
- `tests/`: regression and negative tests.
- `release/baseline_v0_1_core.py`: historic experimental v0.1 reference fixture used by unit/trace verifier, not frozen historical Sutra Core v0.2.2.

### Do not claim

This test uses toy resource units, human-authored domain rules, simulated effect receipts and seeded candidate components. It does not move inventory, send a message, deploy an app, generate unknown code independently or allow itself to approve any release.
