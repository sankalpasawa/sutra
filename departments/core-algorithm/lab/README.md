# Experimental reference — one kernel, 31 extension cases

**Build label:** `sutra-kernel-extensions/0.9.0-stop`. This is an independent study; do not treat it as a released implementation of production Sutra Core or J2/Native. 0.9.0 (Core Algorithm program, 2026-11-13) makes a step that cannot run, or fails, an outcome instead of an error. Until 0.8.0 a handler, the gate or a kind's settle hook that raised in the middle of a plan ended the run with an exception: the steps before it stayed done and paid, the journal got no row, and a second goal never ran. Now (1) the whole step runs guarded, from finding its method to paying for it: whatever the gate finds and whatever the handler raises (any `Exception`) or returns, the step ends as a receipt or as one `STEP_STOPPED` line in the run's hash chain, with the step, a reason and what the step's effect reads (`UNKNOWN` when it cannot be read); nothing after it runs; the run returns status `STEP_STOPPED` (work state `stopped`) with what ran and what it cost, the stopped step and the rest of the plan under `pending`, and `stopped` naming the step and the reason; the journal gets its row, the kinds settle their books, and the next goal runs; (2) a step is paid, in full or not at all, after its receipt is in the record, so a stopped step is never paid and the budget and the provider slots equal the start less the cost of the receipts; (3) what a handler returns is rebuilt as plain data like everything else that is handed in (an object, at most 16 levels), so no code of the handler runs after it returned; a return that is not plain data, or that sets one of the receipt's own fields (`method`, `scope`, `action`, `status`, `sha256`), stops the step; (4) a reason is a phrase from a closed list: `Gate changed before effect: <gate words>`, `Prerequisite not true before effect: <facts>`, `Handler refused: <the handler's own words>` when the handler raised the kernel's `Stop` with one text, `Handler failed: <the error's class>` for any other error (a `RuntimeError` too: Python raises those itself), `Handler returned what cannot be a receipt`, and `Kernel fault: <the error's class>` for an error of the kernel's own code inside the guard; a class is named by the name Python holds for it, read from the type itself so that no code of the class runs, and only when that name is plain (exact text of ASCII letters, digits and underscores that does not start with a digit): any other name is worded `unreadable`; of an error that is not such a refusal the kernel records the name of its class and nothing else (never its message), and it escapes what UTF-8 cannot carry in a handler's words, so the same stop has the same trace root on every machine that runs the same Python version, as long as the handler words its refusal the same way (the words after `Handler refused:` are the handler's own, as a receipt's detail is; a class's name is the running Python's, and Python renames classes between versions: `socket.timeout` is named `timeout` before 3.10 and `TimeoutError` from 3.10 on, so two records of one failure compare only on one Python version); (5) a kind whose settle fails is one `SETTLE_STOPPED` line and is named under `unsettled`, and the other kinds still settle. The design is option B of three, chosen 3 of 3 by independent judges (ruling R18): the declared check of a step and its tries stay outside the kernel. The first review round on this version (two refuters, 19 findings) cut one rule, fixed thirteen findings and left six as stated limits. The first build did not offer a step that rests on a rule's head whose row does not read TRUE; that hid plans 0.8.0 completes and worded a person's no, and a row its rule contradicts, as missing evidence, so the rule is gone and planning is 0.8.0's again. The same round showed a stop line that could not be written for words UTF-8 cannot carry, a deep return that was paid without a line, a vanished provider that left a step half paid, and a return read with the handler's own code. The second round (two refuters, 12 findings: one that blocked release, four to fix, seven notes) fixed nine and left three as stated limits (the band of call depths near the end of the stack, the row an event stores before a hook raises, a class's name by Python version). It broke the naming of an error's class a second time: a class that gave no text for its name ended a look with `TypeError`, or worded its stop with a gate's phrase, so the name is no longer asked of the class. It showed that the verifier took `UNKNOWN` for whatever a stopped run said its goal or its effect reads, refused two honest cases (a journal that holds a row a decision turned away; a candidate made for a second goal), let a stop worded as a kernel fault stand anywhere with any words, held a `SETTLE_STOPPED` row to no shape and refused a prerequisite with the empty name: the verifier is as described below now. Five mutants of the kernel's lines that the tests let live each fail a test now, and the viewer no longer lists the stopped step among steps that were not run. The third round (two refuters, eight findings: three to fix, five notes) did not refute the build, and its findings were settled without new code (ruling R19): six are limits, each stated below and pinned by a unit test as the build behaves today (the name of a kind is taken as it is registered; a plan that must stop is chosen again at every look; a chain of stored rows can use up the stack inside a step; a handler that swaps the provider slots leaves one step with a receipt's line, a stop line and half a payment; the verifier's limits were wider than it said; a blocked run that names no reason passes the verifier); two are closed by assertions, so that thirteen more mutants of the kernel's lines that the tests let live each fail a test now; four comments and one docstring of the kernel and the verifier were corrected to say what the code does; and six fixes that need new code are owed to the next version and listed in `NEXT-GATES.md`. The kernel went from 373 to 387 lines; `State.goal_history`, written on every run and read by nothing, was removed. What changed in the record: the 30 older cases and all event records are byte-identical; case 30 records a stop (the builder's last step names a constructor that no pack declares: three steps run and are paid, the fourth stops). The independent verifier holds a stopped run to the shape of a stop: its three fields; a reason from the list, a failed handler and a kernel fault named by one plain name; the stop row as the last row of the plan and its steps, right after the stopped step's own gate row (one exemption: a kernel fault may stand right after a row of the plan instead, because the kernel can fail before a step reaches its gate); each `SETTLE_STOPPED` row with its two fields, a kind of the registry and one plain name, after the rows of the plan, none on a plan that was only offered, and `unsettled` equal to these rows. It holds every case's books to its receipts and pack files: the budget left; the journal (first the rows the packs turned away, then one row per run in order; any other row is a row turned away during a run and names a fact that carries a decision); the candidates the last run lists, each cited by a receipt; the stored facts (the rows the packs left, except on the effect of a step that ran or stopped, which is its handler's to write); and what the stop row of the last run says its effect reads and what that run says its goal reads, which must be exactly what the stored rows read (the verifier keeps its own copy of the kernel's rule for a row and for a reading, and a unit test holds both copies to the kernel). It refuses 23 forged stops, fourteen of them re-made as a forger would (the run changed, its chain hashed again, every copy updated), and check S49 shows for each of these nine checks which forgeries it alone refuses, and that the last of the 23 is refused only by the line that pins case 30. 0.9.0 also closes the three limits that review round eight of 0.8.0 left (ruling R19: a fix that needs new code goes to the next version): an amount (a cost, a budget entry, a provider's capacity) is a whole number below 10**18, so no sum the kernel makes of amounts outgrows what every Python prints; `execute` must be exactly true or false, and `resolve`, `on_event` and `run_standing` refuse anything else before a row is stored or a step runs (so `answer` does too); a version named inside `depends_on` is held to the rule for a row's own version (a name, a number or null; true, false, a list or an object is refused). The verifier now holds a trace row's `seq` and a run's `pareto_options` to whole numbers by type (true is not 1, 3.0 is not 3) and a `BLOCK` row to its own copy of the kernel's ranking of the ten stop reasons (each reason one of the ten, the row named by the first in rank); S48 holds four forgeries more, each re-made as a forger would, and check S50 shows that each of the three checks is the one that refuses its forgery. Known limits of this version: a plan whose step rests on a fact with no stored TRUE row at its turn (a condition that holds only through a rule; a fact made by a kind that writes no evidence, such as `compile_candidate`) is still offered as `PLAN_READY` and then recorded as stopped, and it is chosen again at every look, also where a dearer plan that would complete stands beside it: a stop does not feed the next plan, the dearer plan is dominated on cost, so the result offers it nowhere (only the trace shows that it was matched and admitted), and the goal never completes although a route exists (0.8.0 chose the same plan and ended every executed look with the error); a stopped step costs nothing, but the steps before it run and are paid: once when they leave evidence, again at every executed look when they leave none, until the budget is gone; an effect a handler wrote before it failed stands (nothing is rolled back), the stop line says what the effect reads, and a later look can complete on that effect although its step was never paid; the guard holds against what a handler raises and returns, not against what it does to the State: a handler is reviewed code and holds the State, and one that breaks the State's own books can still end a look with Python's error: one that removes its own method ends that look, and one that stores a candidate nested deeper than Python can copy ends every later look, dry looks too; such a handler can also break points 1 and 2 with no error at all: one that replaces the State's provider slots by a mapping that cannot be written makes its look return with its own step recorded as stopped (`Kernel fault: AttributeError`) although the receipt's line is in the chain and the budget was paid, with the slot not taken and no receipt in the result (the verifier's check of a stop accepts that stop row; its check of a run against its trace refuses the run, because the trace lists a receipt that the result does not); an error that is not an `Exception` (`KeyboardInterrupt`, `SystemExit`, `GeneratorExit`) is not a step's failure: it passes through the guard of a step and of a settle hook, and the look it interrupts leaves no journal row while the steps before it stay done and paid; a hook is reviewed code and its own error is not the stop of a step: a plan hook that raises while planning (a `Stop` too) ends the look with its error before any step of its goal runs; in a call that runs several goals the goals before it have run and been paid and their results are lost with the error; through `on_event` or the stamp (`answer`) the event's row, the stamp's decision included, is stored before the looks run, so it stands although the call raised and returned nothing, the journal has no row for that look, and the question is closed (its receipt answers nothing more); and a check hook that raises an error the kernel does not turn into a refusal (a `Stop` or a `ZeroDivisionError`, say) leaves `apply` with that error instead of a `ValueError`, the pack not applied; the name of a kind is taken as it is registered: `register` checks a kind's hooks and not its name, and a registry handed to `State(actions=...)` is not checked at all, so point 5 holds for a kind named by text that the record can carry and not for another: when the settle hook of a kind named by text that UTF-8 cannot carry, by bytes or by a frozenset fails, the `SETTLE_STOPPED` line cannot be written and the look ends with Python's error (`UnicodeEncodeError`, `TypeError`), its steps done and paid, the journal without a row and the next goal not run; when the name is a number, null or a tuple the look returns, but the line and `unsettled` carry that value and the verifier refuses the run; and a pack's method can name a kind registered under a number or under null as its `action`, so a receipt can carry that value where a kind's name is meant; a kind named under `unsettled` may be behind its receipts: for the ask kind the question just asked is then not on the books, the asked party's answer is refused, and the next executed look asks and pays again; Python's own limits are not guarded: a look called with the interpreter's stack nearly used up ends with `RecursionError`, and in a band of call depths just short of that the stack runs out inside a step instead, so the look returns with that step recorded as stopped (`Kernel fault: RecursionError`; a handler that uses up the stack by itself is recorded as `Handler failed: RecursionError`, far from the end of the stack too), unpaid, and an effect its handler had already written stands, as after any failure; the same world therefore gives different records by how deep its caller stands, and what the rest of such a look does is Python's own: from 3.11 a later step that needs more stack than is left is recorded as stopped in its turn, while Python 3.9 (older than this lab asks for, but `python3` on the machine that builds it) lets the look go on past the limit once the error was caught and, about fifty calls past it, ends the process with no error to catch (`Fatal Python error: Cannot recover from stack overflow`; seen on 3.9.6, provoked by no test; 3.10 was not run); a chain of stored rows, each resting on the one before, that is long enough to use up the stack gives the same two endings whatever the depth of the caller: a look that reads it while planning ends with `RecursionError`, a dry look too, as on 0.8.0; and where a step reads the chain deeper than planning did, the look returns with that step recorded as stopped (`Kernel fault: RecursionError`), unpaid, at every executed look, and the next goal runs, where 0.8.0 ended the look with the error (on Python 3.9.6 and 3.11.15 a step reads one call deeper than planning, so exactly one length of chain does this; on 3.12.13 a step reads no deeper and no length does); the verifier runs neither the kernel nor a handler and the chain holds no secret, so it does not catch a run re-made consistently from end to end (a stop moved one step earlier, with its receipts and books re-made), a handler's refusal re-worded (the words are the handler's own), a stored row on the effect of a step that ran or stopped changed together with what the run says it reads (that row is its handler's), a stop whose gate admitted the step re-worded with any other phrase of the list that is not a gate's (as a kernel fault, with its gate row left in or taken out; as a failed handler; as a return that cannot be a receipt; as a prerequisite of the stopped step, also one that the stored rows read TRUE, because the facts such a stop names are held to the step's prerequisites and not to the books), a stop re-told as a completed run (its stop row replaced by a `STEP_ALREADY_TRUE` row for the stopped step, its gate row taken out, `pending` and `stopped` gone, although the stored row of that step's effect does not read TRUE), a settle failure invented or erased (a `SETTLE_STOPPED` row for a kind of the registry with its name under `unsettled`, put in or taken out: the record says neither which kinds have a settle hook nor whether a blocked look was dry), a blocked run that names no reason at all and is worded `METHOD_ABSENT` (the kernel's own word for it, which the kernel writes only for a rule with no branch: no pack can deliver one, so it has to be put into the State by hand), or a row said to be turned away during a run on a fact that carries a decision; only case 30's own outcome is held by a pinned line (its status, its reason, three receipts, the pending step, what its goal reads): that line refuses a re-wording of case 30's own stop, a forged case 30 that has no `stopped` field ends the verifier with `KeyError` instead of a failed check, and a settle failure invented on case 30 for a kind that has no settle hook passes; the books keep the facts as they stood at the end of a case, so what a stopped run says its effect and its goal read is held only when it is the case's last run; and the verifier holds a case to the handler contract (`extensions/constructor.py`: a handler writes the evidence of its own effect and a candidate, and leaves the rest of the State alone) and a candidate to a receipt that cites it, as the lab's constructor does, so it refuses the record of a kind that takes budget, writes another fact or stores a candidate its receipt does not cite, and with it two records the kernel can leave: a candidate stored by a step that then stopped (it stands on no receipt), and a stop line that says `UNKNOWN` for an effect that stands (the kernel writes that when it cannot read the effect: a handler removed the step's method, say). 0.8.0 (Core Algorithm program, 2026-11-11) lets a step ask a person and wait, and tightens what the kernel accepts. ### Structure

- `kernel/core.py`: bounded recursive resolver and safe local action boundary; since 0.4.0 it carries no learning, since 0.7.0 only the `simulate_fact` effect and a registry for the rest.
- `extensions/asks.py`: the `ask` action kind with its hooks, `answer` (the stamp) and `open_asks` (since 0.8.0).
- `extensions/constructor.py`: the `compile_candidate` and `emit_artifact` action handlers (out of the kernel since 0.7.0).
- `scenarios/`: authored, reviewed-in-fixture JSON packs.
- `extensions/knowledge.py`, `reflection.py` (with `Learner`, the per-run candidate-only learning since 0.4.0), `j2_projection.py`: bounded proposal utilities, **not** true external data/model/J2 integration.
- `extensions/standards.py`: the evidence adapter: a checklist over a workflow JSON becomes verified evidence rows (source = the adapter, version = the digest of what was checked); it runs when packs are authored, never inside the kernel.
- `extensions/implementation.py`: the implementation generator: from a plan and its state, a workflow in the `sutra-native` user-kit shape, its atoms, the owning department's scaffold and a page; PROPOSED_ONLY, deterministic, writes nothing, runs nothing.
- `tools/`: fixture, run and static-viewer scripts.
- `qa/`: independent verifier (does not import kernel), optional browser tests.
- `tests/`: regression and negative tests.
- `release/baseline_v0_1_core.py`: historic experimental v0.1 reference fixture used by unit/trace verifier, not frozen historical Sutra Core v0.2.2.

### Do not claim

This test uses toy resource units, human-authored domain rules, simulated effect receipts and seeded candidate components. It does not move inventory, send a message, deploy an app, generate unknown code independently or allow itself to approve any release.
