# L10 as built: seed function specs and their tests
Built: `sutra_app/library/specs/function_specs.json` (the five `FunctionSpec`s, version 1, as `{"kind": "function_specs", "specs": {...}}`,
18 KB, the default path of `load_function_specs()`) and `tests/library/test_lib_function_specs.py` (71 cases, 0.3 s).
Content: role, goal, yields, stages, reads, writes, may_not (7 to 9 each), the J2 task kinds with the reply family and kind each
answers with, and the atom templates of docs/design/function-nodes.md section 3 (named checks and work hints). 18 templates
in all (identity 7, adaptation 3, priority 4, coordination 2, audit 2), 20 check references.
The wiring the L1 review asked for already sits in `node.py` (L6: `REGISTRY.bind_function_specs(load_function_specs)`) and
`atom.py` (L4: `bind_check_arity`). The tests prove it works on the seed: `verify_refs()` returns `[]`, a spy arity function is
called once for each of the 20 `CheckRef`s (so the set is not empty), and three broken copies give exactly three violations.

## Decisions
- Template name = task kind (declare's lookup is "the template by (function, kind) else `generic`"). The table row "requester_answered,
  approval, ruling_budget" is therefore three templates with the same goal and checks; the owner's question is the template `answer`
  (not a task kind). Kinds with no template (identity resolve, stage_decision, limit, send_confirm, question; adaptation dispute,
  atom_failed, change; priority dispute; coordination dispute; audit dispute) use `generic`.
- `FunctionSpec.goal` is the role sentence of the agent file's front matter, verbatim (a test reads the file); the library table's
  coordination goal dropped an "and", the file has it. `reads` are the front-matter items, identity without "envelope decisions"
  (FN-24). `writes` use "questions to the Requester" where the file says "CEO questions". `may_not` = the files' "You may not" lists
  plus the "You do not ..." sentence; audit has no list, so its items come from the sentence and the failure patterns.
- Reply references: identity intake/ruling(resolve)/approval (`approval|approval_ask`)/done(audit)/heard(requester_answered);
  adaptation propose/respond/atom_verdict(atom_failed); priority price (price and ruling), envelope_check; coordination schedule;
  audit report. Kinds whose J2 reply has no registered class (limit, send_confirm, question, ruling_budget, stage_decision, the
  disputes, change) name none, so declare adds no `reply-valid` for them.
- `answer-recorded` needs one argument, the question message id, which only the layer knows. The seed holds the placeholder
  `{question_message_id}`; declare must replace it. Tests substitute `14`.
- The seed names the 12 registry checks that are not floors; `reply-valid` and `turn-posted` are never in a template (declare adds them).
- `touches` is `[]` everywhere (function atoms touch nothing, function-nodes.md 2.3). `steps` is empty (declare fills `step_label`).

## Known limits
- `verify_refs()` resolves reply families only after `sutra_app.library.functions` is imported (it registers them); with only
  `node` and `atom` imported it reports `unknown_reply_family` for 13 task kinds. The test file imports it; the engine and L8's
  `all.py` must too before they call `verify_refs()`.
- The test file carries a small stand-in for E6's `declare` (template by kind else generic, floors by work kind) to prove each
  template opens; E6's real declare is tested in `test_engine_fn_declare.py`.
