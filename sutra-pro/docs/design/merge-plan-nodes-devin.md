## 2. The order

Rule: `main` stays releasable. Nothing lands that has not passed `scripts/gate.sh` in the foreground and `sutra-pro-ci` on **the exact commit**. The order follows dependency and readiness.

1. **Now: land nothing.** Keep working. Use the decision blocks of section 4.
2. **Rehearse the meeting once DV-1 is finished** (and again if a branch moves): in a separate throw-away worktree make `integ/sutra-pro-nodes-devin` from the parity head, merge the DV-1 head, resolve as in section 3, run the whole gate and the JS tests. Fix what breaks **in the branch it belongs to**, then delete the throw-away branch. It is never landed. Preview any pair without touching a worktree: `git merge-tree --write-tree --name-only --messages <a> <b>`.
3. **Land nodes first, but only after** the first real-model beta run passed (D347: checks C5 to C11 seen), the whole gate is green on the final head and CI is green on that commit. `main` is where a release is cut, and the first release that carries v6 migrates the owner's real data (section 5), so nodes waits for something real, not only for stand-ins. Landing is a fast-forward (`git push origin feat/sutra-pro-agent-nodes:main`) while `origin/main` has not moved; if it moved, merge `origin/main` into nodes first, run the gate again. If an unrelated urgent release is needed before that, cut it from `main` as it is: it carries none of this.
4. **Land the Devin-parity branch second**, after its small conditions (D363: a way in, the words, two tests), the gate, CI. It is stacked on nodes, so it is a fast-forward onto the new `main`. Its v7 and v8 come after v6; a test pins the order.
5. **Land DV-1 when it is ready.** It does not depend on nodes and has no migration, so it is the lowest risk of the three and may go before nodes if it is ready first. Whichever lands later merges `origin/main` into its branch first (`AGENTS.md` step 1) and resolves section 3. Default: nodes, parity, then DV-1, so the small branch's developer, who is still in it, does the merge.
6. **Release, only when the owner says so, one release for all three**, flags `0`, never marked Latest, beta first: `scripts/py scripts/install_app.py beta` from the integration head, tried beside the stable app, then `scripts/release.py`. Why one: every release that carries a migration is a one-way door (an older app refuses a newer database); one release is one door (v5 to v8), three would be three. Before it: M1 (the migration on a copy of the owner's real data), R12 (the notes read against the release head), P9, the owner's `sutra-pro backup --to <folder>`. If the parity branch is not ready, the owner may choose nodes plus DV-1 (v6 only) and a later release for v7 and v8: a second door, the owner's call.

If a landed branch turns out bad: a new commit on `main` that reverts it (`git revert`), never a force-push and never a deleted tag (`AGENTS.md`).

## 5. Data and rollback

`sutra-pro` takes a `pre-upgrade-v<old>-to-v<new>.sqlite3` backup before it migrates (`ops/backup.py`) and refuses a database from a newer app. So the first release with these migrations is the door: the way back is a backup taken before it, not a downgrade. M1 (open the beta on a copy of `~/.sutra-pro`, as `docs/RELEASE.md` allows) is the only way to see the v5 to v8 migration on real data; it has not been done.
