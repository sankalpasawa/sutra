# Design: one engine that keeps gaining capabilities, and a chat session of its own for every agent
_Status: Proposed · Date: 2026-11-09 · Branch: feat/sutra-pro-project-work · Supersedes: D125 part (1) and the "engine unchanged" line of D121 · Read: docs/notes/PROJECT-WORK.md, DECISIONS D121-D125, docs/design/{orchestrator,engine,connectors,ui,j2-sync-3}.md and the code named below (all verified in this tree on 2026-11-09)_

Owner requirements, kept verbatim in intent. **R1**: one central engine that keeps being amended; a new capability enhances the old ones and is inherited by all of them; no rerouting. **R2**: every agent and subagent works in a new chat session of its own, and that session has its own model and effort, linked to how Claude desktop does it (NON NEGOTIABLE).

## 2. Part A: engine capabilities (R1)

### 2.1 The capability registry (D126)
New package `sutra_app/engine/capabilities/`. A capability is a small object the engine always runs; it can add, never replace.
```python
class Capability:                                   # capabilities/base.py
    name: str
    def outputs(self) -> dict[str, OutputSpec]: return {}          # new output types, merged into j2.OUTPUTS
    def install(self, ctx: EngineContext) -> None: ...             # once per run process, after j2 is imported, before J2Run exists
    def tag(self, tag: CallTag, ctx) -> dict: return {}            # extra CallTag fields for this call (llm.ask)
    def progress(self, tag: CallTag, event: dict) -> None: ...     # sees each progress event of a call
    def addendum(self, fn: str, ctx) -> str: return ""             # system text for agent fn (ctx.output says which output)
    def select(self, brief: str, ctx) -> Optional[Selection]: ...  # a vote on the output when it is "auto"
@dataclass(frozen=True) class OutputSpec: ...                      # the keys of a j2.OUTPUTS entry, plus single: bool and workspace: "read"|"edit"; .to_j2() -> dict
@dataclass class EngineContext: task, settings, paths, data_dir, output (property: the run's concrete output)
CAPABILITIES = (WorkspaceCapability(), ProjectCapability(), AgentPicksCapability(), AgentLiveCapability())    # capabilities/__init__.py, fixed order
def register(j2) -> None        # idempotent; merges every outputs() into j2.OUTPUTS; raises CapabilityConflict on a name that exists
def install(ctx) -> None        # per-process: install() of each, then appends tag/progress hooks to llm.TAG_HOOKS / llm.PROGRESS_HOOKS
```
Rules that make R1 structural: (1) the registry is the only way the host, the API and the tests learn what the engine can do (`GET /api/engine/capabilities` lists name, outputs, settings); (2) `tag()` may only fill fields that are empty on the tag and `register` refuses an existing output name, so no capability can override another; (3) every hook runs for every agent call of every output, so a new capability is inherited by all of them with no change to any caller; (4) a capability has one setting at most (`workspace: auto|off` today) in `EngineSettings`, default on. Adding the next capability is one module and one line in `CAPABILITIES`.
Wiring (the engine's own files, not vendored): `llm.py` gains `TAG_HOOKS` and `PROGRESS_HOOKS` lists; `ask()` merges `tag()` results into the tag and composes `on_progress` with the progress hooks (a call with a hook gets `partials=True` for text calls); `host/loop.py _make_run` calls `capabilities.register(j2)` then `capabilities.install(ctx)` before `J2Run(...)`; `engine/views.py` calls `register(j2)` right after `from . import j2` (so the API process, the stdlib adapter and tests see the same outputs); `host/publisher.py HostHooks.system_addendum` returns the inner text plus every capability's `addendum`.

### 2.2 The `workspace` capability (D127)
Every engine agent call gets the owner's working folder with read tools and the project's CLAUDE.md; edit and git tools only where the output allows. The policy is data in the tag, the decision is in the router.
* `engine/port.py CallTag` gains `workspace: Literal["", "read", "edit"] = ""`: the most this call may do in the folder.
* `WorkspaceCapability.tag`: `{}` unless `settings.workspace == "auto"` and `tag.purpose in ("agent_turn", "plan", "judge")` (helpers such as summary, template, review, change get no folder). For the five functions and every `W-n` builder: `"read"`; for a builder whose output's `OutputSpec.workspace == "edit"` (only `project`): `"edit"`. Audit is always `"read"`, so it verifies independently of the builders. It reads no file and needs no folder: it is a table.
* `Router.folder_for(tag) -> Folder | ""` replaces `AGENT_FUNCTIONS`: `want = tag.workspace`; none -> `""`; `grant = self.chat_folder()` (the owner's folder with `.edit` from `access`, `""` offline or when none is set); result is the grant when `want == "edit" and grant.edit`, else `Folder(path, edit=False)`. **The owner's access setting always caps the capability**: with "read only" a project builder cannot edit. The org chat agent keeps its folder by tagging its calls `workspace="edit"` in `connectors/orchestrator_port.py` (the same cap applies); `AGENT_FUNCTIONS` is deleted.
* Plumbing: `_text_call` and `_schema_text` (the engine's two paths) pass `folder=` to `call_text` / `_oneshot_plan` (`base.py call_text` gains the `folder` keyword it lacks); `_json_call` uses `folder_for` instead of the tuple; the router adds `scan(grounding_text(folder))` to the system text after the egress check, so J2's own prompt, its `calls.jsonl` record and every prompt golden stay byte for byte. `engine_port.port_from_config` sets `router.folders = WorkFolder(data_dir, cfg.resolved_work_root())` for a live port. The engine process reads `<data>/connectors/workdir.json` per call, so a folder chosen mid-run applies from the next call. Offline and the stub: no folder.
* Setting: `EngineSettings.workspace: Literal["auto", "off"] = "auto"` (team `engine.json` can switch it off; cost: about 3k tokens of grounding per call and a tool loop per call).
* **Amendment (D135, after the first real run).** The folder text of an agent whose own tools only read said "They are read-only", and Identity copied it into the charter as the RUN's limit although the owner had allowed changes. `CallTag.team_workspace` (`none`, `read`, `edit`) is set on EVERY agent call of an output whose spec says its builders edit (`workspace.team_workspace_for`; project only); `Router.folder_for` caps it by the owner's access into `Folder.team` (`edit`: the builders may change files and the owner allowed it; `read`: they would but the owner chose read only; empty: no statement); `workdir.grounding_text` then says what the TEAM may do. With `edit`, an agent that only reads is told its tools do not change files because the builders do, that this is not a limit of the run, what the builders can do and that it plans for it; with `read`, every agent is told the owner chose read only in Settings, under Working folder, that nobody can change a file, and that the report then gives the exact edits and how to allow changes. A call with no team gets the old words byte for byte, so no other output and no prompt golden changes. `CallTag.workspace` also has a fourth level, `inspect` (the file tools plus Bash restricted to the four git reads with the edit deny list, nothing that writes): `workspace_for` gives it to Audit of an output whose builders edit, so "check every claimed change with `git diff`" can be done; the owner's access caps it (read only: no command at all), `Folder.git` carries it and the claude connector turns it into the tools.

### 2.4 The engine chooses the output itself (D129)
`EngineSettings.output` becomes `Literal["auto", "website", "prd", "hld", "lld", "project"]`, default **`auto`**. `auto` is decided once, in the host, before `to_env()` and before J2 is imported, by `capabilities/select.py choose_output(brief, has_folder, seed_output) -> Selection(output, rule, reason)`, a pure function (so no model call and no new J2 prompt):
1. the owner chose (page select, team `engine.json`, `data/engine.json`: anything but `auto`): that output, reason "you chose it";
2. strong project words (repository, repo, codebase, source, git, branch, commit, pull request, CLAUDE.md, the folder, the app's code, refactor, bug) -> `project` (with no folder set Identity says where to choose one, rule from PROJECT-WORK root cause 4);
3. `seed_from` is a finished run of another output (a follow-up change request): keep that output;
4. a make-a-deliverable phrase (write/draft/create/make/produce/generate/build/design + PRD/HLD/LLD/website/site/landing page) -> `website` (J2's default; J2's own `detect_documents` still plans the documents, exactly as today);
5. a folder is set (`WorkFolder.get()`) and nothing above matched ("check the app and update the J2 prototype") -> `project`;
6. else `website` (today's behaviour for a team with no folder).
The host writes the concrete output into `settings.json`/`to_env()` (J2 never sees `auto`), writes `<run>/output.json {choice, output, rule, reason, folder: bool}`, a `output.selected` trace line, and, only when the result is `project`, a `system` line in the run's chat: "Working on this as project work in your folder (you asked about a repository; choose another kind of result in the start page if that is wrong)." `website` selections post nothing, so existing runs, events and goldens do not change.
Owner override: per team in `engine.json` (`output`), globally in `data/engine.json`, per request in the start page's select (E19: options "Let the team decide" (auto), Website, PRD document, Project work), and per task through `TaskSettings.J2_OUTPUT`. Changing the default key from `website` to `auto` changes nothing for a team without a folder and without project words; a team whose `engine.json` already says `output: website` keeps it.

## 3. Part B: a chat session of its own for every agent (R2)

### 3.1 What a session is for an agent (D130)
* **Who**: the five function agents and every workflow builder (`W-n`); any future agent is any name the engine tags a call with and announces with a `step` event (`team:<role>` already exists), which the projector already turns into a step node and session. Nothing is added for them.
* **New session per run** (the owner's "new chat session"): a builder's step session is made with its node in the same transaction (`ensure_node`, already true) and is stamped with the run; a function agent's session is the node's active session (invariant I1 stays: one active session per node) and is **rolled** at the agent's first event of a run: if the active session was used by an earlier run, `AgentSessions.open` archives it and starts its replacement in the same transaction through the existing `ChatArchive._replace` (which now also carries `pinned_model` and `pinned_effort`), then stamps `run_id` and the title. A session with no lines is only stamped, so nothing churns. The past run's sessions stay readable in the archive (kind function/step, `unarchive` is refused for them like a legacy chat) and are listed with their run.
* **Title by the agent**: function `Identity · <task title, 40 chars>`; builder `W-3 · <workflow name>`. **When it opens**: a builder at its `step` event (registration, before it works), a function agent at its first `node`, `say` or `usage` event of the run, all through the one helper `AgentSessions.open(tx, task_row, node_id) -> session_id` that the projector's `_on_say`, `_on_node`, `_on_usage`, `_note` and `TaskGraph.ensure_step` call instead of reading `chat_session_id`.
* **Shows**: its own `say` lines (already routed), its usage rows (`usage_ledger.session_id` is already the node's session, so per-session usage is a `GROUP BY`), and live partials (3.5).
* **Owner can steer** (3.4); the session stays `writable = 0` (the record rule stands); the owner's line goes through the steer route, not the generic message route.

### 3.2 Schema version 4 (migration `_v4` appended to `MIGRATIONS`, additive: three `ALTER TABLE ... ADD COLUMN`, no table rebuild)
```sql
ALTER TABLE chat_sessions ADD COLUMN pinned_model  TEXT NOT NULL DEFAULT '';
ALTER TABLE chat_sessions ADD COLUMN pinned_effort TEXT NOT NULL DEFAULT '' CHECK (pinned_effort IN ('','low','medium','high','xhigh','max'));
ALTER TABLE chat_sessions ADD COLUMN run_id TEXT;                     -- the run an agent's session belongs to (function and step sessions)
CREATE INDEX chat_sessions_run ON chat_sessions(run_id) WHERE run_id IS NOT NULL;
ALTER TABLE tasks ADD COLUMN pick_json TEXT NOT NULL DEFAULT '';      -- the run-level choice for agents that have none
```
`ChatSession` record gains `pinned_model`, `pinned_effort`, `run_id` (validator: model/effort empty when `pinned` is empty); `chats.py _SESSION_COLUMNS`, `ChatSessionOut`, `ensure_node` and `ChatArchive._replace` carry them. `SCHEMA_VERSION` follows `len(MIGRATIONS)`, so the doctor, backup manifest and tests move with it. Existing rows get empty values: nothing is backfilled and every old chat keeps working (its model and effort stay in `session.json` as before).

### 3.3 Model and effort honoured by the engine (D131)
**The choice** is a triple `Pick(provider, model|None, effort|None)` (`connectors/models.py`); `""` provider means "Default". `ChatChoices` keeps `get(sid) -> provider` (the router's `choice_source`) and gains `set_pick(tx, sid, provider, model, effort)` and `pick(sid)`.
**Cascade** (a whole pick replaces, never field by field): the agent's own session pick > the run pick (`tasks.pick_json`) > the team's pick (the department chat's pill, live) > the policy default (`policy.json`, `model_for`, effort rules). The page labels the source: "own choice", "this run", "the team", "default".
**Channel**: the server writes `<run>/choices.json` (atomic, 0600; the engine only reads, like `inbox.jsonl` is only written by the server):
```json
{"schema": "agent-choices/1", "rev": 7, "default": {"provider": "claude", "model": "sonnet", "effort": "high", "from": "run"},
 "agents": {"identity": {"provider": "codex", "model": "gpt-5.6-luna", "effort": "medium"}, "W-3": {"provider": "claude", "model": "haiku", "effort": "low"}}}
```
`default` is the run pick else the team pick (or null); `agents` holds only the agents with a choice of their own, keyed by the name the engine tags (`identity`, ..., `W-3`). One module, `connectors/agent_picks.py`, owns the shape for both sides: `build_choices(...)` and `write_choices(path, body) -> bool` (skips an identical body) used by the server, `AgentPicks(path).for_tag(tag) -> Pick | None` (re-reads on a changed `(mtime_ns, size)`, validates, ignores a bad file with one warning) used by the engine. The server writes the file at task start (beside `task.json`, `tasks.py`), when an owner's pick changes for a live run (agent session, `PUT /api/tasks/{id}/choice`, or the team's pill), and for every live task at start-up (`reconcile`): the database is the truth and the file is rebuilt, so a server restart loses nothing.
**Router** (`connectors/router.py`, one change set): `Router.agent_pick: Optional[Callable[[CallTag], Optional[Pick]]]`; `_plan` consults it when there is no chat session id and `tag.purpose in ("agent_turn", "plan", "judge")` (summary, template, review, change keep the policy); a pick makes its provider the first of the order (the existing `pinned` path), its `model` goes through `connector.resolve_model` for that provider, and `Plan` gains `pick` and `effort_for(provider)` (the pick's effort for the picked provider only, else the policy's), which `_text_call`, `_schema_text` and `_json_call` use instead of `plan.resolved.effort`. If the picked provider or model cannot run, the plan falls back by policy and the call's usage `note` says "your choice for identity (codex) could not run: not signed in; claude answered" (the existing `connector.choice_unavailable` event is also kept). A change applies from the agent's **next call**, never mid-call or mid-retry. The engine wires it in `AgentPicksCapability.install`: `router.agent_pick = AgentPicks(run_dir / "choices.json").for_tag`.
**Validation** at the pill: `RouterChatPort.check_choice(provider, model, effort) -> Choice` is extracted from `choose` (provider ready, model in `model_options`, effort in that model's efforts, with the valid ones named in the 422) and is pure. `PUT /api/chats/{sid}/choice` is unchanged for a direct chat (it still calls `choose`, writes `session.json`) and now also stores the triple in the database; for a function or step session it calls `check_choice` only (no router session is created: the engine's calls are one-shot) and stores the triple.
**Claude desktop mapping** (the pill is the existing `chat_pill.js` + `model_pick.js`, extended, not rebuilt):
| Claude desktop | Sutra Pro |
|---|---|
| each session has its own model and effort selector in the composer | every agent chat has the pill (provider, model select, effort select) above its box, also when the owner cannot type |
| the choice belongs to that session and applies to its next turns | stored on the agent's session; applies at its next model call; survives restart (database) |
| model list grouped (main rows, then more models), efforts per model | `ModelOption.group` main/more and the efforts of the chosen model only (`efforts_of`), unchanged |
| "Default" follows the app setting | a first "Default" button clears the choice and shows what it resolves to: "Default: Sonnet, high (from the team)" |
| a subagent is its own thread | every agent and builder is its own session, listed under the team and the run |
| a new thread per task | a new session per run (3.1) |

### 3.4 The owner steers an agent from its chat (D132)
Recommended and chosen: the agent chat gets a "Note to <agent>" box. `POST /api/chats/{sid}/steer {text <= 2000}` (token required; only a function or step session of a live task, else 409 "that run is over") in one transaction stores the owner's line in the session (`role user`, `meta {steer: true}`) and writes `<run>/node_context.json[<agent>]` atomically as the owner's notes, newest last, capped at 2,000 characters, passed through the egress scan. The engine already appends that text to the agent's system prompt on every call (`system_addendum`, P9, `## Node context`), so the note reaches the agent at its next call with no new engine protocol and no inbox line; the prompt goldens are untouched because the file does not exist in them. A question that Identity asks the owner is still answered in the team chat (unchanged). The page says "the agent reads this at its next step".

### 3.5 Live view of the agent's calls (D133)
No ninth event: partials are ephemeral and chatty, and the event protocol is a contract. `AgentLiveCapability.progress` keeps, per agent, the text so far (tail 4,000 characters), the last tool line and a tool count, and a daemon thread rewrites `<run>/agent_live.json` (`{"schema": "agent-live/1", "at", "agents": {"W-3": {"call", "since", "text", "tool", "tools"}}}`, atomic) at most 4 times a second; an entry is removed at `call_finished`. `connectors/router.py _progress` also forwards `tool_call` events as `{"tool": title}`. `RunWatcher.tick` reads the file when its mtime changed and publishes `chat.partial {session_id, message_id: 0, who, delta: <text>, reset: true, tool}` per agent (session through `AgentSessions`, cached per run), plus `{reset: true, delta: "", done: true}` when the entry goes; the stored line arrives later from the `say` event. A JSON reply streams raw JSON, so the page shows the tool line and "writing its reply" for a text that starts with `{` and the text itself otherwise (`ChatPill.streamParts`).

### 3.8 Usage, limits, restarts, stop ladder, invariants
* **Usage and limits**: rows already carry the agent's session id; per-session figures come from the grouping above. Provider quota and the start gate (`Limits.gate`) stay per provider and per team; a pick on a provider at its limit falls back with the note above, never blocks the run.
* **Stop and restart**: stop ladder (inbox `stop`, then SIGTERM, then SIGKILL) is unchanged; sessions, picks and the run folder stay; a follow-up run is a new task, new run folder, new `choices.json` from the database, and its agents open (roll) new sessions carrying their pick. A server restart re-adopts the live process (reconcile) and rewrites `choices.json`; an engine process that was running keeps its last file, which is correct because the file is derived from the database. A crashed run's sessions are final.
* **Invariants that must not break**: I1 (one active session per node and `chat_session_id` equals it; a roll is archive plus replace in one transaction), I2 and I7 of `check_graph`, `chat_sessions_active` unique index, the `ChatSession` record rules, the projector's idempotency by `(session_id, src_ref)` (a replayed line after a roll lands in the current session and is dropped as a duplicate), "SQLite is written by the server only" (the engine reads files). New: **I8** every active function or step session of a live task has `run_id = task.run_id` after its agent's first event; **I9** `choices.json` keys are the five functions or `W-n`, every provider is claude or codex, effort is in the five.

## 5. Decisions (paste into docs/DECISIONS.md in this form)
## D126 — One engine, extended by capabilities that every agent and every output inherit; nothing is routed in front of it
- Sources: owner requirement R1 after the first fix; D125 part (1) (superseded), D121 ("the engine's runs are unchanged", superseded), D13 (the vendored engine is changed only by numbered patches), D14 (one process per run, files only).
- Decided: Words to a team always start the department run of the one engine. New abilities are added to the engine through a capability registry (`engine/capabilities/`): a capability can add outputs, call-tag fields, prompt addenda, progress sinks and one setting; it cannot replace another's; every agent call of every output runs every hook. The API-level route to "the team's own turn" (`work_route.py` and its parts) is removed.
- Why: a front door that guesses from words splits the product in two (a document engine and a second path), and every later ability would need a third; one engine with inherited abilities is what the owner asked for and keeps the five-function flow, audit and receipts for project work.
- Rejected: keeping the route and tuning its words (two flows, wrong whenever the words mislead); asking the owner which mode each time; a plugin system with a manifest and loading from disk (a fixed tuple in code is enough, and nothing is loaded from the owner's folder).
- Diagram: key label "one engine, capabilities add", pill on the Department runtime box.

## D127 — The workspace capability: every engine agent call may read the owner's folder, only project builders may change it, the owner's access setting caps both
- Sources: R1, D121, D125 parts (2) and (3), `router.AGENT_FUNCTIONS`.
- Decided: `CallTag.workspace` ("", read, edit) is set by the capability (five functions and all builders: read; builders of an output whose spec says edit: edit; helper calls: none); `Router.folder_for(tag)` turns it into the folder, capped by the `access` the owner chose, and adds the project's CLAUDE.md and the folder text after the egress check; `AGENT_FUNCTIONS` is deleted (the org agent tags its own calls). `EngineSettings.workspace: auto|off`.
- Why: the folder and its rules belong to the connector layer, the agent and output belong to the engine; a tag carries one to the other without either learning the other's names, and J2's prompts stay byte for byte.
- Rejected: a list of function names in the router (what failed); giving the folder from the host to the whole process (no per-call least privilege); appending the folder text through `system_addendum` (it would change every prompt golden and be logged as J2's prompt).
- Diagram: key label "agents read your folder", pill on the Connector router box.

## D128 — "Project work" is an engine output built on the document flow; the one vendored change is patch P14
- Sources: R1, engine.md 3.4, `OUTPUTS` in `j2.py`.
- Decided: `OUTPUTS["project"]` is registered by the capability: sections Findings, Changes, Verification, Open items, Outcome; its own intake, builder, plan, atom rules, rubric, conditions (an absolute path outside the vendored folder), mocks and addenda; builders work with their tools and report, Audit verifies in the folder. `single: True` plus patch P14 (`_plan_stages` returns early) stop named documents from swapping the output. Rates reuse `rates_prd`.
- Why: the document flow already has intake, planning, building, auditing, three attempts, receipts and nodes; a work report is a document whose sections are done with tools, so almost everything is inherited; one recorded line replaces a runtime patch nobody could verify.
- Rejected: a second flow beside the document flow; a runtime monkeypatch of `_plan_stages`; editing `conditions/`, `rates.json` or the role files (they are byte-checked); a test-running Bash allow-list (D125 keeps tests for the owner).
- Diagram: key label "Project work output", pill on the J2 chips box.

## D129 — The engine picks the output for a brief itself; `auto` is the default and the owner overrides it anywhere
- Sources: R1, PROJECT-WORK root causes 1 and 4, the settings cascade of engine.md 4.4.
- Decided: `EngineSettings.output` defaults to `auto`; the host decides once, before J2 starts, by a pure rule table (owner's choice, strong project words, a follow-up's own output, a make-a-deliverable phrase, a set folder, else website); the result is written to `settings.json` and `output.json` and, for project work only, said in the run's chat. The start page select gets "Let the team decide" and "Project work".
- Why: the decision must be inside the engine and before the first prompt (the intake prompt depends on the output); a rule table costs no model call, is testable, and leaves every existing run unchanged.
- Rejected: Identity choosing in its intake reply (the reply format and prompts are golden); a model call to classify (cost, latency, nondeterminism); no default (the failure the owner hit).
- Diagram: key label "engine picks the output", pill on the Department runtime box.

## D130 — Every agent works in a chat session of its own, new for each run
- Sources: R2, I1 (orchestrator.md), D63, D123.
- Decided: builders already get a step session with their node; function agents' sessions roll at the agent's first event of a run (archive the used one, start the replacement in the same transaction, carry the choice); sessions are stamped with the run, titled by the agent and the task or workflow, and listed per team and run (`GET /api/teams/{dept}/agents`). Past runs' agent chats stay in the archive, read only.
- Why: the owner wants each working agent to have its own thread like a Claude desktop subagent; the existing one-session-per-node invariant and archive-and-replace machinery do it without a new table.
- Rejected: one endless session per function (a thread that mixes every run); a new graph node per function per run (breaks the team's fixed five); a separate sessions table.
- Diagram: key label "a chat per agent per run", pill on the Chat sessions box.

## D131 — Each agent session has its own provider, model and effort, honoured by the engine through a file the server writes
- Sources: R2, ABS-6/8 (direct chat pill), Claude desktop's per-session picker, ORCH-D5 (SQLite is the server's).
- Decided: schema v4 stores `pinned_model` and `pinned_effort` beside `pinned`; the cascade is own > run > team > policy default, a whole pick at a time; the server writes `<run>/choices.json` and the engine's router reads it per call (`connectors/agent_picks.py`), applying it from the agent's next call and falling back with a visible note; the pill is the existing one plus "Default".
- Why: the engine is a separate process that must not open the database; a small file rebuilt from the database survives restarts and is the same pattern as the inbox.
- Rejected: the engine reading SQLite read-only (two writers' view of one schema, locking, a path the child environment lacks); keeping model and effort only in `session.json` (a temp folder that can vanish and that the engine cannot see); a per-field cascade (hard to explain in one chip).
- Diagram: key label "model and effort per agent", pill on the Connector router box.

## D132 — The owner steers an agent with a note in its chat, delivered through the engine's node-context file
- Sources: R2, P9 (`system_addendum`), the `ChatSession` rule that function and step chats are not writable.
- Decided: `POST /api/chats/{sid}/steer` stores the owner's line and writes the agent's entry of `<run>/node_context.json`; the engine appends it to that agent's system prompt from its next call; the generic message route stays read only for these chats.
- Why: it uses a seam that exists, needs no new inbox kind and no change to the engine protocol, and says honestly when it applies.
- Rejected: letting the owner post as a normal message into an agent chat (breaks the record rule and implies the agent answers at once); a new inbox kind that interrupts a running call (cannot be honoured mid-call); sending the note to Identity only.
- Diagram: key label "note to an agent", pill on the Chat sessions box.

## D133 — An agent's live work reaches its chat through a published file and `chat.partial`, not a ninth run event
- Sources: R2, engine.md 4.5 (eight event types), D111 (one streaming mechanism).
- Decided: the engine rewrites `<run>/agent_live.json` (at most four times a second) and the watcher turns it into the existing ephemeral `chat.partial` events for the agent's session; the stored line still comes from the `say` event.
- Why: partials are many and not durable; the protocol and its contract tests stay as they are; the page already knows `chat.partial`.
- Rejected: a `partial` event in `events.jsonl` (log growth, contract change); polling the run folder from the page (a second reader of engine files).
- Diagram: key label "live agent chats", pill on the Chat sessions box.

## D134 — Claude desktop is the reference for the picker: per session, applied next turn, "Default" follows the team, subagent equals thread
- Sources: R2, `model_catalog.py` (model groups and efforts per model), D111.
- Decided: the mapping table of 3.3 is the contract; the labels and efforts (low, medium, high, xhigh, max) are the CLI's own; "Default" shows what it resolves to and from where.
- Why: the owner linked the behaviour to Claude desktop; one table makes it testable.
- Rejected: a separate "advanced" panel; a global model switch for all agents (that is the team pill).
- Diagram: key label "same picker as Claude", pill on the Chat sessions box.
