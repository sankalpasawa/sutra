# Engine design: the department runtime (the J2 engine) and its API
_Status: Proposed · Date: 2026-11-04 · Baseline: J2_Prototype `ce2631fb` (2026-11-03, clean tree; the prototype moved to `33aeeda` on 2026-11-04 and that is what is vendored: see docs/design/j2-sync.md) · Verified with Python 3.11.14, fastapi 0.162, pydantic 2.14.2 · Section of docs/DESIGN.md · Read: J2 code, `arch/gen.py`, DECISIONS D1-D12, and the sibling sections `orchestrator.md` (ORCH), `ui.md`, `library.md` (LIB), `connectors.md` (CN), as they stood at 00:50. The settlements S1-contracts, S2-models, S3-web and S4-fnodes are applied and binding: every changed paragraph, table row or code block carries its settlement id in square brackets, so `grep -n 'S1-contracts-03' engine.md` shows where it landed. The final function-node design is `docs/design/function-nodes.md`; function nodes plug in through 4.3 and 4.3a [S2-models-05]._

## 1. Purpose and scope
**In.** The program that does a department's work: J2's loop J2.a..J2.h run by the five functions, the workflow builders and all the code around them (D4); the process that runs it (`python -m sutra_app.engine --run-dir`, D9); the model seam to the connector layer; the events and files it writes for the orchestrator's watcher; the files it publishes so the J2 pages can read a live run; the 28 data routes (23 GET, 5 POST) of the J2 pages with unchanged paths and shapes, mounted once at the root, the department in `?dept=` (J2's own index and d3 routes are the UI's, 7.1) [S1-contracts-01], plus the two engine-settings routes (7.1 rows 31-32) [S1-contracts-03]; the function-node layer that turns each function turn into one work atom (`fnodes/`, 4.3a) [S2-models-05]; continuing a finished run (`seed_from`); the port of J2's three test scripts.
**Out** (sibling sections; contracts in 4.9): task and run lifecycle, spawning, SQLite, the watcher, SSE, chat sessions, graph store (orchestrator); pages, static files, the J2 page edits (ui) [S3-web-10]; closed models, `gate_record`, atom lifecycle, function-node specs (library); connectors, router, sign-in (connector section).

### 4.3a The function-node layer (`fnodes/`) [S2-models-05][S2-models-06][S4-fnodes-02][S4-fnodes-03][S4-fnodes-04][S4-fnodes-05]
The layer is `sutra_app.engine.fnodes.layer.FunctionNodeHooks(EventHooks)`. It runs inside the engine process (WPs E6 and E8; E7 proves a whole run) and writes every transition as one `atom` event (4.5); the server's Projector turns those events into rows (ORCH-6), and the library supplies the data and the pure functions (`FunctionSpecs`, `Atom` and its lifecycle, the reply families, `FunctionNode`). The design is `docs/design/function-nodes.md`; this section is the engine's side of it.
**Grain.** One atom per function turn; rules in `docs/design/function-nodes.md` section 5 (grain 5.1, hooks 5.2). Work kinds `llm`, `bash`, `manual`; the manual atom follows a turn that ends paused. Only the five function names open function atoms; J2's re-asks inside the turn are tries of the same atom, planner, judge, summariser, reviewer and template-spec calls are charged to the open atom and are not atoms, and builders `W-n`, the code validator and the confidence judge open none (builders keep J2's `atom/1`). Hooks used: `run_started`, `turn_started`, `call_finished`, `message_posted`, `record_saved`, `turn_finished`, `run_status`, `run_error`. There is no `run_ended` hook: the layer abandons its own open atom on the normal and error paths through `run_status` and `run_error` (reason `run ended: <status>`), and the server abandons the rest when the task ends in any way (S1-contracts-10). Every hook body is wrapped: an error becomes a `layer.error` trace line and never reaches J2 (no `fatal` flag is ever set).
**Checks.** Checks are the registry of `docs/design/function-nodes.md` section 4: 14 names, pure functions, evidence from the hooks only (`registry.py` and `evidence.py` in E8; `checks.py` runs them in E6). Exit codes 0, 1, 127.
**Refuse.** A refused open is stored, ledgered and carded and the turn goes on without an atom (trace type `atom.refused` with the refusal code). Production templates never refuse, so a refusal is a template or registry bug made visible. Ids: `ids.py` counts per (run, node) from 1 and every open attempt consumes a number, a refused one too, so gaps are normal.
**Mode.** Version 1 observes and J2 stays byte-identical; `docs/design/function-nodes.md` section 5.4 has the detail. (1) An atom closes only through passing checks: the library's `close_atom` is the only place a state becomes closed, and no flag or caller can skip a card or a ledger row. (2) J2's own code keeps enforcing replies and routes (re-ask once, repair, drop, template, `_pick`) and that stays the default; the closed reply models (`reply-valid`) and `HANDOFFS` (`turn-posted`) are the oracle the registry judges the outcome by, so a violation can no longer pass unseen, but J2's behaviour is not changed. (3) Write scope is warn-and-log: at `message_posted` a message by a function with no open atom, and at `record_saved` a record outside `FunctionSpec.writes`, write one `layer.touches_miss` trace line and block nothing; it flips to hard only when the golden runs show none (a later decision). (4) `SUTRA_NODES=on|off|enforce`: on is the default, off selects `EventHooks`, enforce is reserved and the factory raises `ValueError`; `system_addendum` stays empty, so the prompt goldens stay byte-identical. Not in v1: enforce mode and builder atoms; write scope: warn-and-log in v1.

`EventWriter` appends each line with one `os.write` on an `O_APPEND` descriptor, so the watcher never reads half a line, and stamps `at` on every line. The inbox is polled every 150 ms. **Inbox rule.** Lines are read in `n` order into a FIFO; each tick delivers the head (`user` to `run.user_says`, `override` to `run.apply_override`); a `False` result leaves the line at the head and writes one `inbox.deferred` trace line (a normal path: the `say` event of a question is written before the run thread has finished its last steps and set status `waiting`, so an immediate answer must wait). A `stop` line is handled the moment it is read, ahead of the FIFO, and discards everything queued behind it (section 6, F5); a `setting` line (`{"kind":"setting","decide_for_me":bool}`, D152) is applied the moment it is read, ahead of the FIFO and whatever the run is doing, with `J2Run.set_auto`, and discards nothing; lines that arrive after `run.ended` are never read. A `user` line is delivered only when `run.status == "waiting"` (paused, or finished but not yet ended) [S1-contracts-13].

### 4.7a The steps at the end of a run (`host/finish.py`, D142 and D143)
`finish.run_steps(host, status)` is one call in `Host._conclude`, after `publisher.stop()` and before `heartbeat.stop()`: the heartbeat still beats while the steps work, and the final publish and `run.ended` come after every file a step writes. It does nothing unless the run ended `done` or `done_with_open_items` (a stopped or crashed run gets no step and no file). Steps, in order: `agent_views`, `j2_agent_views.build(<run folder>, quiet=True)` (`agent/*.json`, `agent/audits/A-n.json`, `artifacts/<name>.json`, `site/sections/<id>.json`, the stamped `prd.json`, `hld.json`, `lld.json`, `design.json`, and `<output>.json` of a document output: `project.json` for a project run), and `catalog`, `j2_template_lib.collect(<team runs folder>, runs=[run_id])` inside `j2_template_lib._library_lock()` (skipped, with the reason in its trace line, when `template_library` is off, for a mock run, when the run folder has no `templates.json`, or when the lock stays taken for its 30 s wait). A step that raises (a `SystemExit` included) or takes more than 10 s is one `finish.step` line in `trace.jsonl`, `{step, result: ok | skipped | failed, seconds, ...facts, why | error, slow?}`, and never a failed run; a step over the limit ends the rest. The limit is checked when a step returns: a step is never cut short from outside, which would leave a half-written file. `finish.py` imports no J2 module at import time, because the host sets J2's environment before J2 is first imported.

### 4.8 Continuing a finished run (`rehydrate.py`, P11)
`rehydrate(run, src_dir) -> dict` copies the source folder's JSON, JSONL, `site/` and `artifacts/` files (not events, trace, inbox, logs, snapshot, live) into the new run folder, then sets: `chat` (copied `chat.jsonl` without its header), `goal`, `stamped`, `workflows`, `conflicts`, `audits`, `sections`, `style`, `sites` (from `site/v*.html|md`), `request` (summary `brief`), `calls`, `cycle`, `spent`, `budget`, `receipts`, `decisions`, `done=True`, `status="waiting"`, `outcome`, and, when `realization.json` exists, `real`, `real_base` (a deep copy of `goal`), `real_summary` (the `summary.json` realization block minus `applied`) and `real_asked=True` (needed only for `J2_CHANGE=1`). The first message is then a change request (`user_says` marks `change`, j2.py:3371-3375). It raises `RehydrateRefused(reason)` unless the source `summary.json` status is done or done_with_open_items, the `chat.jsonl` header says output website, the source has no document chain (no `documents.json`, no `stage-*.json`) and `goal.json` and `workflows.json` exist. Realization on or off is not a condition: the earlier pause had a measured cause that is not a rehydrate defect (section 2, last row). Refusals stay for unfinished, stopped and crashed sources, document chains and unreadable files; a run stopped while it waited for the owner cannot be rehydrated (S1-contracts-15), so its follow-up starts fresh with the old files and the orphaned-question rule (the orchestrator puts the question in `framing`). A follow-up is always a new task with a new run id, folder and process; the old folder is never written again. Refusal is not an error: the run starts fresh with the old files as `upstream` and one plain `system` line. The two `system` lines are fixed: `Continuing from run <id>: the team keeps its charter, workflows, findings and site and treats your message as a change request.` and `Starting a new run. ## 6. Flows
**F1 A task from start to end.**
1. The orchestrator allocates the run id, creates the run directory (mode 0700), writes `task.json` atomically (0600), creates empty `inbox.jsonl` and `events.jsonl`, and spawns `python -m sutra_app.engine --run-dir <dir>` in a new session with the one env allowlist shared with the connectors (their `PASS_NAMES` plus `SHELL`, `TERM`, `PYTHONPATH`, every `SUTRA_*` except `SUTRA_TOKEN`, and the seven task keys; never an `*_API_KEY`, `*TOKEN*` or `*SECRET*` name) [S1-contracts-11].
2. The host runs 4.7 steps 1 to 9; the first model call is the Identity intake of J2.a.
3. Every `post` appends `chat.jsonl` and, unless it is the owner's, a `say` event; every model call is tagged (with its atom id), goes through `ModelPort` and, when it is a `J2Run.call`, is appended to `calls.jsonl`; every model request (helper calls and failures included) becomes one `usage` event, written by the router's sink [S1-contracts-05]; every `save` marks the publisher dirty.
4. The publisher (250 ms) rewrites `snapshot.json` and `live.json`, builds `j2_map` and emits `node`, `step` and `atom/1` events for what changed (the function-node layer writes its own `atom` events at each transition). The watcher (400 ms) projects them; the page polls `/api/state?dept=web` every 700 ms and reads the files [S3-web-12].
5. Identity asks the owner: the `say` event has `act: "ASK_REQUESTER"`, the J2 run is `waiting` and paused, the process stays alive. The owner's answer reaches the inbox as a `user` line; the host calls `user_says` (once the run is `waiting`, by the inbox rule of 4.5), which resumes at `paused["to"]` (j2.py:3436-3446).
6. The run ends (Done, done with open items, a limit the owner ended, or a crash): final publish, `run.ended`, exit 0.
**F2 Page poll.** `GET /api/state?dept=web&since=n` [S3-web-12]: `resolve_run(None, "web")` gives the live or latest run; read `snapshot.json`; return the chat from `n`. Files missing (the host is still starting): `idle_snapshot`. `?run=<id>`: saved mode, folder only.
**F3 The owner writes in the department chat.** `POST /api/say?dept=web` [S3-web-12] calls `deliver_to_department(dept, text, settings=page.next_settings)` and clears `next_settings` after a delivery that created a task: a waiting live task gets an inbox line (200 `{"ok":true}`); a running one raises Busy (409 `{"ok":false}`, J2's behaviour); no live task creates a follow-up task (F4).
**F4 Follow-up after Done.** The new task has `seed_from` = the old run. The host tries `rehydrate` (4.8). Success: the old folder's files are copied, `user_text` is a change request, J2's change path runs (Adaptation proposes a new workflow, builders, Audit, Done again), events start again from `run.started`. Refused (unfinished, stopped, crashed, document chain, files missing): a fresh run with the old site and documents in `upstream/<old run id>/` and one `system` line saying so (the two `system` lines are fixed, 4.8). Never an error [S1-contracts-12].
**F5 Stop.** The server sends `{"kind":"stop"}`: the host handles it the moment it reads it (ahead of the FIFO, which it discards), sets `stopping` before it closes the port (so J2Run's crash path skips the reviewer call and the report), calls `port.close()` (kills an in-flight CLI), waits for the run thread, sets the outcome "Stopped: stopped on request", rewrites `summary.json` status to stopped, final publish, `run.ended{stopped}`, exit 0; the whole stop finishes inside 6 s. If the server escalates, SIGTERM does the same without waiting [S1-contracts-15][S1-contracts-13].
**F6 Server stop and start.** A graceful shutdown stops every live run by the one stop ladder (S1-contracts-15: `stop` line, 8 s for `run.ended`, SIGTERM to the process group, 4 s, SIGKILL; worst case 12 s; the task takes the status of `run.ended` if one was written, otherwise it becomes stopped with the outcome "the app was closed"; a follow-up continues it from the old files, F4) [S1-contracts-15]. After a server crash a run whose process lives keeps running (files only, no pipe) and the orchestrator's `reconcile` re-attaches from `events_offset` and the pid; a run whose process is gone and has no `run.ended` becomes crashed (ORCH 5.1; the reconcile rules of S1-contracts-16). The page shows the last `snapshot.json` with the process-gone rule of 4.6.
**F7 Failures.**
- a *Model call fails* (the router already retried and fell back): `ModelError` propagates through `J2Run.call` to `_run_safe` (j2.py:3415-3429): system message `Stopped: <Type>: <300 chars>`, outcome "Crashed: ...", `summary.json` crashed, report, `error` set; the host emits `say` for the system line and `run.ended{crashed, code:<the ModelError code>}` [S1-contracts-09]; the page shows its error state and "Try again". A `StructuredOutputFailed` inside an artifact call is J2's per-attempt failure (j2.py:7095), not a crash.
- b *CLI missing or not signed in*: caught at startup by `port.preflight()` (step 5): a `system` line and `run.ended{crashed, code:"start_failed"}` with the outcome "could not start: Claude CLI not found on PATH (install it and run claude once)" (no `run.started` was emitted), exit 3 [S1-contracts-09]; the owner sees the line in the department chat. Mock runs skip it. If it fails later in a run, path a with code `cli_missing` or `not_signed_in`.
- c *Run thread dies* (SystemExit, MemoryError; `_run_safe` catches only Exception): the excepthook sets `error`, status waiting, and the main loop ends the run as crashed.
- d *Process dies* (OOM, SIGKILL, segfault): no `run.ended`; the heartbeat stops with the process; the orchestrator marks the task crashed by the rules of S1-contracts-16 (process gone after one final drain; outcome "the team process stopped unexpectedly" with a redacted stderr tail of up to 2 KB; a silent but alive process is not killed); the page shows the last snapshot with the process-gone rule [S1-contracts-16].
- e *Invalid JSON*: a model reply that is not JSON follows J2's own fallbacks (`call()` keeps `{"say": raw[:400]}`, j2.py:3171-3175; builders retry inside their envelope). A bad `inbox.jsonl` line is skipped with an `inbox.skipped` trace line; a missing run directory or an invalid `task.json` ends the run as crashed with code `start_failed`, exit 2 [S1-contracts-11]; a torn `snapshot.json` cannot occur (atomic rename), and a missing one means idle.
- f *Disk error* writing the run folder: `OSError` in `post` takes path a. *Chrome missing*: J2's behaviour, the render check "could not run" and the site is never workable (README.md:247). *Library busy for 30 s*: P10, generic template. *Record rejected* (library strict mode): `RecordRejected` has `fatal = True`, so it crashes the run through path a; in log mode it only writes a `record.warning` trace line.
**F8 Two departments at once.** Each has its own process, folders, memory, environment, `NAMES`, `RATES`, `OUTPUT`. The only shared writable store is the library (P10).
**F9 Reset and output on the start page.** `POST /api/output?dept=web {type}`: allowed while the page has no run (idle) and writes `page.json.next_settings.J2_OUTPUT`; otherwise 409 (J2: `set_output` is refused once a message exists, j2.py:2883). `POST /api/reset?dept=web` calls `stop_live(dept)`: False (a task is starting or running; nothing is touched) gives 409 `{"ok":false}` (J2, j2_server.py:264); True (nothing of the department is starting or running afterwards; a task waiting for the owner was stopped through the normal ladder with the outcome "reset by you", queued and blocked tasks were cancelled) writes `page.json.since_run` = the latest run id (atomic) and answers 200 `{"ok":true}`. No other state is cleared and history is never deleted (tasks, run folders, the department chat), so `resolve` returns idle until the next task; the history stays in `/api/runs`. The next task after a reset is a fresh run: `_follow_up` reads `since_run` and does not seed from, or make a child of, a run at or before it (no `seed_from`, no `parent_run_id`, no framing from an old open question); a run made after the reset is continued again [S1-contracts-04][S3-web-12].

### 7.2 Routes and run selection
Layout: `api/__init__.py` (`mount`), `ports.py` (`EngineServices`), `ctx.py` (`build_ctx`), `reply.py` (`Reply` to `Response`, charset, no-store, redaction through `services.redact`, the security headers below), `state.py` (3, 4, 5, 20, 21, 33, 34), `run_views.py` (6-9, 14, 18, 19, 35, 36, 40), `library.py` (10-12, 37), `files.py` (13, 15-17, 22-25, 38, 41, 42), `commands.py` (26-30, 39, 43), `settings.py` (31-32) [S1-contracts-03]. Every J2 handler is a plain `def` (FastAPI runs it in its thread pool) of three lines: `ctx = build_ctx(services, dept, run)`, `reply = VIEWS[name](ctx, q)`, `return to_response(reply)`; writes (POST and PUT) add `Depends(services.require_token)`.
**Where the routes live.** `mount(app, services)` calls `app.include_router(router)` once: the J2 paths live at the root. The dependency `dept_dep` reads the query parameter `dept` only and fullmatches `DEPT_ID_RE` (`^[a-z][a-z0-9-]{1,39}$`, defined in `engine/spec.py` and also used by `TaskSpec.dept_id`): missing or malformed gives 400 `{"error":"dept_required"}`; `services.department(dept)` returning None gives 404 `{"error":"not_found"}`; an archived department (`getattr(dept, "archived", False)`, dormant while no department can be archived, S2-models-14) answers reads and refuses writes (say, output, reset, playbooks/clear, lessons/clear) with 403 and the ORCH envelope code `read_only` [S3-web-12][S3-web-10]. There is no path prefix, no `X-Sutra-Dept` header, no cookie and no default department. Every J2 route, including `GET /api/refs` and `GET /api/library`, requires `?dept=` (the page's fetch wrapper adds it to all J2 paths), so no route is special-cased; the two settings routes (31, 32) are not J2 paths: there `dept` is optional and means this department's file [S1-contracts-01][S1-contracts-03]. Root-level collisions checked: the orchestrator's `GET /api/runs/{run_id}` differs from J2's `GET /api/runs`; no other J2 path is used by ORCH, LIB or CN.
**Headers.** `to_response` (`api/reply.py`) adds `X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer` to every response and, for content type `text/html` (rows 17, 24 and 25: generated sites, html artifacts and rendered documents), `Content-Security-Policy: sandbox allow-scripts allow-forms allow-popups; frame-ancestors 'self'`, so generated content cannot read the page token; no response sets a cookie. Consequence accepted: a generated site that uses localStorage, cookies or fetches the app's own API fails inside the preview, and J2's own checks run it outside the app [S3-web-14].
**How a request picks a run** (`build_ctx`; the department was already checked by `dept_dep`, above): 1 `?run=<id>`: must match `j2-[\w-]+` and `resolve_run(id, dept)` must return it (another department's run is 404); mode **saved**, read-only from disk, also while it is running (J2's rule, j2_server.py:79-81). 2 No `run`: `resolve_run(None, dept)` gives the live run, else the latest, ignoring runs at or before `page.json.since_run`; found: mode **live**; none: mode **idle**. The client never sends a path. The folder is `services.data_dir / ref.dir`.
