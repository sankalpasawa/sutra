# Coverage critic: what the design and the build do not yet cover

_Written 2026-11-04 by the coverage critic. Evidence: the built code on `main` (45 of 49 packages merged; ORCH-6, ORCH-7, ORCH-8 and CT-1 are treated as pending, not as gaps), the as-built notes `docs/notes/*.md`, the five design sections, the settlements S1 to S4, `function-nodes.md`, `DECISIONS.md` D1 to D90, `build-plan.json`, the J2 prototype at `33aeeda`, the Sutra plugin `bin/sutra-atom` and `hooks/atom-floor.sh`, the owner's draw.io page 3 and `docs/diagram/gen.py`. Nothing outside this file was changed. Three claims were run, not only read: the two `xfail` tests of `tests/engine/test_engine_fn_golden.py` (both still xfail), a glob walk of `sutra_app/` against `[tool.setuptools.package-data]`, and a read of `default_env_file` / `project_root` in `config.py` and `engine/paths.py`._

## How to read this

- **Severity.** High: the app as the owner will run it does not do what the owner rules say, or something the owner needs to run it at all is missing. Medium: a real function or safeguard is missing but the app runs. Low: noted, no package proposed.
- **Work packages.** Every high and medium finding names a proposed package `GAP-*`. `owns` lists only paths that no package in `build-plan.json` owns today, plus the package's own note `docs/notes/GAP-*.md` (the plan tool requires it). Several fixes must edit files that a MERGED package owns. Those are listed as **Transfers** in the spec: when the package is added to the plan, move those paths out of the merged package's `owns` into the new one (the merged package is history; `plan_tools.py check` refuses two owners). Chassis files (`pyproject.toml`, `README.md`, `docs/DESIGN.md`, `docs/TRACEABILITY.md`, `docs/DECISIONS.md`) cannot be owned by any package: they are named as **Chassis edits** to be made by hand.
- **Decided, not asked.** Where a choice was needed the spec says what was chosen and why. Candidate decision text for `DECISIONS.md` is in section 6.

## 3. Findings

### G01 (high) A default run has no function atoms
- **Source.** `docs/notes/E7.md` findings 1 and 2; `tests/engine/test_engine_fn_golden.py` lines 265 and 273 (both `xfail`, re-run here: 2 xfailed); owner rule "each function is an agentic node with the plugin's work-atom behaviour".
- **Evidence.** `sutra_app/engine/host/loop.py:344` calls `factory(writer=, notify=, validator=, node_context_file=, spec=self.task)`; `sutra_app/engine/fnodes/layer.py:374` defines `factory(writer, notify, validator, node_context_file, task, ...)`. The `TypeError` is caught (`except Exception`), one `publish.error` trace line is written, and the host runs with the plain `EventHooks`. Every real run therefore has **no function atoms, no cards, no Atom log rows, no function-node usage attribution**, and everything downstream (ORCH-6 projector, UI-6 drawer, CT-1) is built against the layer that does not run. Second defect: a `stop` line or SIGTERM never calls `hooks.abandon_open("stopped")`, so the manual atom of an unanswered question stays open at `run.ended`.
- **Missing.** The fix and a test that goes through the host's own factory call (E7's tests use a `SUTRA_HOOKS` adapter that hides the bug).
- **Package.** GAP-W1.

### G02 (high) The wheel does not carry the function specs
- **Source.** `docs/notes/L6.md`, `L8.md`, `L10.md` ("Chassis owner: add `library/specs/*.json`"); D86; `pyproject.toml`.
- **Evidence.** A glob walk of `sutra_app/` against the nine `package-data` globs leaves exactly two unmatched files: `engine/VENDORED.md` (allowed) and `library/specs/function_specs.json`. `library/node.py:441` (`DEFAULT_SPECS_PATH`) reads it at import of the registry's `verify_refs`, at `refresh_function_nodes` (startup) and in the layer factory. An installed app (D88, `uv tool install`) has no such file: the server cannot start the function nodes and every run ends "could not start". `tests/test_packaging.py` (ORCH-8) will fail on this, but ORCH-8 cannot edit `pyproject.toml` (protected), so the build agent will be blocked.
- **Missing.** One glob.
- **Chassis edit (by hand, before ORCH-8 merges).** Add `"library/specs/*.json"` to `[tool.setuptools.package-data] sutra_app`. Package GAP-W1 adds the test that proves it from a built wheel.

### G03 (high) Installed app: `.env` is looked up in site-packages
- **Source.** D88 (installed under `~/.sutra-pro`), D11/ORCH-D9 (override key), `config.py:default_env_file`, `engine/paths.py:default_env_file`, `launcher.sh`.
- **Evidence.** Both `default_env_file` functions return `project_root() / ".env"` where `project_root()` is the folder that holds the `sutra_app` package. In a checkout that is the repo; in a `uv tool install` it is `.../site-packages/`. The macOS launcher sets `SUTRA_DATA_DIR` but not `SUTRA_ENV_FILE`. So `J2_OVERRIDE_KEY` (budget +N, ship, drop) and `J2_SMTP_*` (live sends) cannot be configured in the installed app unless the owner knows to set `SUTRA_ENV_FILE`. The same two functions decide where redaction looks for secrets (`orchestrator/redact.py`).
- **Missing.** Default `<data_dir>/.env` when the package is not in a checkout (same rule as `default_data_dir`), mode 0600 check, a template.
- **Package.** GAP-W1 (the rule) and GAP-OPS-1 (`sutra-pro config init`, G09).

### G04 (medium) The Sutra read tools open the wrong file
- **Source.** `docs/notes/CN-3.md`, `CN-4.md` ("`SUTRA_DB_RO` = `<data_dir>/sutra.db` is an ASSUMED name"); D35.
- **Evidence.** `connectors/claude.py:368`, `codex.py:541` and `tools/profiles.py:128` pass `<data_dir>/sutra.db`; `Settings.db_path` is `db.sqlite3`. `tools/sutra_tools.py:185` raises "no database" when the variable is unset; with the wrong name the default read model opens a missing file. A model that is given the Sutra tools can read nothing of the org chart, atoms or usage. No test catches it because CN-8's tests build their own database.
- **Package.** GAP-W1 (one constant `DB_FILENAME` shared by `config.py` and the profiles; a test that starts the MCP server over a database made by `Database.migrate()` and reads a chart row).

### G05 (high) No end-to-end scenario wires the real packages
- **Source.** Task (e); `orchestrator.md` "Scripted conversation" and 5.6; `UI-9.md` ("the real-app run is NOT here"); `E3.md`; `E7.md`.
- **Evidence.** `test_scripted_conversation.py` (ORCH-8) uses `ScriptedConnector` and `FakeLauncher` ("in-process, no subprocess"): the engine is replaced by a script of events. The packages that exist and run for real are tested in pairs only: host + J2 + layer in `tests/engine` (no server), projector against recorded `run_events.jsonl` (no process), router + fake CLIs in `tests/connectors` (no chat agent), chat agent with a scripted port (no router). Nothing runs: chat message, chat agent, router (fake `claude`), chart change, department creation, five nodes, a real `python -m sutra_app.engine` process in mock mode with the function layer, the events file, the watcher, the projector, atoms with cards, the Atom log, usage rows with atom ids, SSE order, a question and its answer through the department chat, `run.ended`, the audit verdict. Also untested with real processes: a server restart in the middle of a run (reconcile), the stop ladder on a real engine, two departments at once under `max_runs`, a follow-up that rehydrates.
- **Missing.** The scenario suite (spec GAP-E2E, section 4 below traces the seven steps).
- **Package.** GAP-E2E.

### G06 (medium) No browser walk against the real app
- **Source.** `UI-9.md` deviations ("run the walk against that app"), D85.
- **Evidence.** `test_browser_smoke.py` and `test_visual.py` run on `tests/ui/fake_backend.py`. The `-k real` case was left for "whoever merges ORCH-7 and ORCH-8"; no package owns it. The first run of the hello-resync rule, the hash CSP with the real pages, the token header, the sandboxed site frames and `EventSource` reconnect against the real SSE are therefore unproved.
- **Package.** GAP-E2E-UI.

### G07 (high) No live smoke, and the design waits on live evidence
- **Source.** D8 ("live runs only on request"), task (e) "a final live smoke test with the real CLIs"; settlements S1 to S4 `unresolved`; `CN-3.md`, `CN-4.md`, `L8.md`, `E1.md`, `E3.md`.
- **Evidence.** Four packages wrote `live` tests (`connectors/test_live.py`, `orchestrator/live/test_live_chat_agent.py`, `library/test_lib_live_transport.py`, `engine/test_engine_live.py`); only CN-9's was run (once, by hand). Nobody owns running them together or the whole-app run. Decisions that are waiting on live data, each with a coded fallback that nobody will switch without a measurement: (1) `anyOf` ops in `--json-schema` / `--output-schema` (`CHART_OPS_TRANSPORT` flat or union, S2-models-04); (2) a real rehydrated follow-up with realization on (else add `realization == 0` back, S1-contracts-12); (3) the rate at which real J2 replies fail the closed reply classes (G14); (4) image input through `claude -p` and Codex `-i` (J2 README: "implemented but not yet tried"); (5) a model calling the Sutra MCP tools (CN-3, CN-8); (6) `--max-budget-usd` behaviour; (7) Codex native schema against the real API; (8) browser behaviours measured only in Chrome 156 (G10). Also the 15 live branches of J2's own `docs/j2-test-plan.md` (T1 to T15) have no counterpart.
- **Package.** GAP-LIVE (run only on the owner's go-ahead; with the owner away it is written and dry-run against the fakes, not executed).

### G08 (high) No operator surface, no single-instance guard
- **Source.** D12 ("`python -m sutra_app` (or `scripts/run.sh`)"), D88, `orchestrator.md` 6.5 (CLI), `REL-2.md` (launcher has `app.pid`), `E3.md` (heartbeat), `orchestrator.md` 5.1 (reconcile).
- **Evidence.** (a) `scripts/run.sh` is promised by D12 and does not exist; no start or stop script for a checkout. (b) ORCH-8's CLI is `python -m sutra_app [--port N] [--data-dir D] [--offline] [--no-browser]` only: no `doctor`, `status`, `stop`, `config`. (c) There is no instance lock in the server: the macOS launcher keeps `app.pid` in bash, but `sutra-pro` started from a terminal does not. Two servers on one data folder both write SQLite (the design's "server is the only writer", D16), and the second one's `reconcile()` sees the first one's live runs, finds their heartbeats fresh and re-attaches a second watcher at the stored `events_offset`, so every line is projected twice; if a heartbeat is late it runs the stop ladder on a healthy run. (d) First-run and sign-in problems are seen only after the first chat message fails (X1/F1). J2's `SETUP.md` has a prerequisites table (Python, Claude CLI logged in, Chrome optional, `J2_CHROME`); nothing in the new app checks any of it.
- **Package.** GAP-OPS-1.

### G09 (medium) Locked settings and secrets have no way in
- **Source.** `engine/spec.py:209` (`LOCKED_FIELDS` = `send_mode`, `send_cap`, `milestone_emails`, `test_email`, `test_slack_target`, `chrome`, ...), D18, J2 `.env.example`, `SETUP.md`.
- **Evidence.** Locked fields are not editable in Settings and come only from `data/engine.json`; the only way to change them is to hand-write JSON in the data folder. There is no template for `.env` (the old `.env.example` was dropped with D7) and no list of which names the app reads (`SUTRA_*` 14 names, `J2_OVERRIDE_KEY`, `J2_SMTP_*` 5 names).
- **Package.** GAP-OPS-1 (`config show | set | init`), documented by GAP-DOCS.

### G10 (medium) The default browser is unverified
- **Source.** `S3-web` unresolved ("Chrome 156 only"), `UI-*.md` limits, `launcher.sh` (`open http://127.0.0.1:...`), `__main__` opens "the browser".
- **Evidence.** Hash CSP, `EventSource` reconnect with `Last-Event-ID`, the sandbox header, `color-mix(in srgb, ...)` in the new CSS and J2's page were measured in one browser. On macOS `open <url>` uses the default browser, which for most users is Safari. Nothing prefers a measured browser or tells the owner.
- **Package.** GAP-OPS-1 (`browser.py`: prefer Chrome when installed, `--browser default|chrome` and `SUTRA_BROWSER_APP`; doctor warns when only an unmeasured browser exists); GAP-LIVE adds a manual Safari checklist item.

### G11 (medium) Logging and error pages
- **Source.** `orchestrator.md` 4.2 (`data/logs/server.log`) and 5.1 step 1 ("logging with the redaction filter"); `config.py` (`logs_dir`, `log_path`); `launcher.sh` (rotates `app.log` at 5 MB); `E4.md` limits.
- **Evidence.** Seventeen modules call `logging.getLogger(...)`; no module configures a handler, a formatter, rotation or the redaction filter (`grep` for `RotatingFileHandler`, `basicConfig`, `dictConfig` in `sutra_app/`: none; ORCH-8's `wiring.py` is where the design puts it, one sentence). `uvicorn`'s access log would print the query string, which can hold `?run=` and `?dept=` (not secrets) but also any future token-bearing URL. No request id ties a log line to a response. Browser navigation to an unknown path gets FastAPI's JSON `{"detail":"Not Found"}`; only `/d/<unknown>/` has an HTML 404 (`ui/routes.py:_not_found`). `E4.md`: headers and redaction are not applied to the framework's own 404/405/422. No diagnostics bundle a non-expert owner could attach to a bug report (version, doctor result, redacted log tail, schema versions).
- **Package.** GAP-OPS-1 (`logsetup.py`: handler, filter, rotation, request-id middleware, uvicorn log config, `mount_ops`); GAP-CONSOLE (HTML 404/500 page for `Accept: text/html`, diagnostics download).

### G12 (medium) No cost and usage view for the owner
- **Source.** Draw.io/diagram box "Usage and cost ledger: one row per call, by atom"; D37, D59, D60; `ui.md` route table ("`GET /api/atoms/log` no view in v1"); owner interest in cost per atom (diagram router box: "cost per atom: usd and tokens").
- **Evidence.** The server stores every call with its atom id and offers `/api/usage` and `/api/usage/summary?by=dept|fn|provider|day|atom`, the `usage.recorded` event and `/api/atoms/log`. No UI file reads `/api/usage*` or `/api/atoms/log`. The owner sees a per-node usage line in the drawer and J2's per-run spend; there is no answer to "what did this week cost, which team and which function, Claude usd versus Codex tokens, how close am I to a quota window" and no way to browse the append-only Atom log the diagram draws.
- **Package.** GAP-CONSOLE.

### G13 (medium) No backup, restore, export or retention
- **Source.** Task (e); D5 (SQLite plus files), D88 (data in `~/.sutra-pro`); `function-nodes-spec.json` risk 1 ("a retention rule is needed (not designed)"); `S4-fnodes` unresolved ("retention of atoms, cards, usage rows and Atom log rows"); J2 `runs/` was 138 MB.
- **Evidence.** The data folder holds the only copy of the org chart, every chat, the atom log and every run. There is no backup command, no restore, no consistent copy of a WAL database while the server runs, no backup before a schema migration (`Database.migrate()` walks `user_version` in place; a failed migration or a newer file raises `SchemaError`), no export of the chart or a department's deliverables, no pruning of bulky run files (screenshots, `trace.jsonl`, `run.stdout.log`, old `events.jsonl`).
- **Package.** GAP-DATA.

### G14 (medium) Reply classes and write-scope names are not tuned
- **Source.** `E7.md` findings 3 and 4; `S4-fnodes` unresolved 1; `E6.md`.
- **Evidence.** In the recorded Brew Lab mock run 9 of 31 function atoms end `verify_failed`, all by `reply-valid` (Identity intake on the answer, Adaptation proposals, Priority prices): the closed reply classes are stricter than the replies J2 accepts. The design says to loosen the classes (L5), never the check. Real replies are untested (G07). 12 `layer.touches_miss` lines appear for records J2 writes legitimately (Adaptation and Priority save `conflicts.json`, Identity saves `workflows.json`) because `FunctionSpec.writes` / `WRITE_TERMS` do not name them. A node log full of red atoms on a green run is noise the owner will learn to ignore, which defeats the point of verify.
- **Package.** GAP-TUNE.

### G15 (medium) Follow-up after Done for a document chain
- **Source.** `engine.md` 4.8 and phase E1-b ("inside E1, after the first green merge: lift the `rehydrate` limit for document chains until the `xfail` test passes"); `tests/engine/test_engine_rehydrate.py:391` (`xfail(strict=True)`); owner rule "everything in J2".
- **Evidence.** E1 merged without E1-b. After a finished PRD/HLD/LLD chain the owner's follow-up starts a fresh run with the old files as `upstream`: the team does not keep its charter, workflows and findings as J2 does for a change request. The text says refusal is "not an error", but this is a J2 capability that the app drops for one of the five output types.
- **Package.** GAP-E1B.

### G16 (medium) Documentation for running the app
- **Source.** Task (e) "README and run instructions"; J2 `SETUP.md` (199 lines), `README.md`; `plan_tools.py PROTECTED` names `docs/DESIGN.md` and `docs/TRACEABILITY.md`.
- **Evidence.** `README.md` is the repo's three lines plus an install command. `docs/DESIGN.md` and `docs/TRACEABILITY.md` do not exist in the repository or in its git history (`git log --all -- docs/DESIGN.md docs/TRACEABILITY.md` is empty) although the plan tools, the brief and the sections refer to them. There is no document for: prerequisites and first run, every flag and variable, the data folder layout, backup, what each Settings group does, how to read the graph/atoms/cost, troubleshooting by symptom (CLI missing, signed out, port busy, second instance, quota, `could not start`).
- **Package.** GAP-DOCS, plus the chassis edits in its spec.

### G17 (medium) Nobody runs the installed app
- **Source.** D86, D88, `RELEASE.md` ("`sutra-pro --help`" only), `REL-1.md` follow-ups.
- **Evidence.** D88 says the finished app is installed with `uv tool install` and is on PATH; D86 says a non-editable install proves the wheel carries every data file. The CI `package` job only runs `--help`. No script installs, upgrades or removes, and no test starts the **installed** copy offline, loads the Home page, creates a team and stops it. G02 and G03 are exactly the faults this finds.
- **Package.** GAP-INSTALL.

### Low findings (no package)
- **G18 `enforce` mode (D52, S2-models unresolved 5).** The owner rule says "verify is the teeth"; version 1 makes the atom the thing that fails, never the turn (`SUTRA_NODES=enforce` raises `ValueError`). That is a recorded, vetoable decision with a stated way back. Recommendation: decide it after GAP-TUNE and GAP-LIVE have produced the false-failure rate; enable enforcement per check, starting with `charter-stamp`, `pass-needs-proof` and `within-budget` (checks whose J2 recovery already exists), never the floors. Do not start before the rate is near zero.
- **G19 quota knowledge per process (S1-contracts unresolved 4).** A Claude quota window learned by one run is unknown to the next run and to the chat agent; each re-learns with one failed call, then falls back to Codex. Acceptable; a shared `data/connectors/health.json` (atomic write, 60 s read cache) is the small fix if delays show up in GAP-LIVE.

## 6. Decisions to add to `DECISIONS.md` (chassis, by hand)
- **D91 Excluded J2 material.** The older three-agent studio and the negotiation demo are not part of J2's loop (no J2 module imports them); the explainer pages, the flow picture and the solar mock are copied as reference only to `docs/reference/j2/`; "everything in J2 is present" means the loop, its data, its page and its tests. Rejected: porting the studio or the demo as pages. Diagram: key only.
- **D92 Browser choice.** `sutra-pro` opens Chrome when it is installed, because only Chrome is measured; `--browser default` opens the system default. Diagram: key only.
- **D93 No retention of database rows in v1.** The Atom log and the usage table are append-only and small (about 100 KB a run); `prune` removes only bulky files of finished runs. Revisit when a real run's size is known (GAP-LIVE).
- **D94 One instance per data folder.** An advisory lock `app.lock` plus `app.pid`; a second launch opens the first instance. Rejected: letting two servers share a folder (double projection after reconcile).
- **D95 Default `.env` beside the data.** Outside a checkout the file is `<data>/.env`. Rejected: a file next to the installed package.
