## 2. Product outcome

After J1 creates a department, the department can work toward its stamped goal as a controlled loop:

- Adaptation proposes the next workflow.
- Priority grants, refuses, or counters within the envelope.
- Identity settles unresolved conflict against the goal and rules.
- Root validates and registers granted workflows.
- Coordination runs one workflow at a time.
- Audit checks the filed result against Identity.
- Adaptation proposes again until the done-when condition holds.
- Identity is the only function that speaks to the user.

The user can understand what the department is doing, inspect the function-to-function exchanges, answer a permitted ask, stop work, and see why the goal is or is not complete.

## 3. User point of view

### 3.1 The normal journey

```mermaid
sequenceDiagram
    actor U as User
    participant I as Identity
    participant A as Adaptation
    participant P as Priority
    participant R as Root
    participant C as Coordination
    participant W as Workflow
    participant D as Audit

    Note over I: 1. Check stamped Identity
    I->>A: Identity is good enough; start
    A->>A: 2. Select Library template or shape workflow
    A->>P: 3. Propose next workflow
    alt Priority grants
        P->>R: Granted workflow
    else Priority counters
        P->>A: Counter within envelope
        A->>P: Accept or reshape
    else No agreement or bound reached
        P->>I: 4. Escalate conflict
        alt Identity can rule
            I->>P: Decision from goal and rules
        else Identity cannot rule
            I->>U: One clear ask
            U->>I: Answer
            I->>P: Decision
        end
    end
    R->>R: 5. Validate and register on department record
    R->>C: Registered workflow
    C->>W: 6. Assign next slot
    W->>C: File result and run evidence
    C->>D: Result available
    D->>I: 7. Finding against Identity
    alt Done-when holds
        I->>U: 8. Goal reached
    else Gap remains
        I->>A: Finding and remaining gap
        A->>P: Next proposal; repeat from step 2
    end
```

### 3.2 What the user sees

The department screen has two coordinated surfaces:

1. **Identity chat** — the user-facing conversation. Only Identity speaks here. It reports starts, decisions, asks, blocks, and completion in plain language.
2. **Agent activity** — a chronological, read-only operational board. It shows the interaction among Identity, Adaptation, Priority, Coordination, Audit, Root, and workflows.

Each activity row shows:

- actor and recipient;
- action and short result;
- state: pending, running, waiting, granted, refused, blocked, failed, or complete;
- the related cycle, proposal, workflow, run, and evidence links;
- elapsed time and envelope usage where applicable;
- a human-readable reason for a decision;
- an expandable payload with structured inputs and outputs.

The activity view must not show hidden chain-of-thought, scratchpads, secrets, credentials, or unredacted external data. “Reason” means a concise decision record tied to rules and evidence.

### 3.3 Example visible exchange

For a department whose goal is “Publish a verified finance-news highlights site each morning,” the activity view can show:

| Actor → recipient | Visible event |
|---|---|
| Identity → Adaptation | “Identity is sufficient. Done when: five current, sourced highlights are published by 08:00.” |
| Adaptation → Priority | “Propose Source finance feeds, extract claims, verify dates, and publish five cards.” |
| Priority → Adaptation | “Counter: use two sources and one publish run within today’s envelope.” |
| Adaptation → Priority | “Accepted. Reduced source scan to two feeds.” |
| Priority → Root | “Granted within calls, money, and time limits.” |
| Root → Coordination | “Workflow passed standards and is registered on this department.” |
| Coordination → Finance highlights workflow | “Slot 1 assigned.” |
| Workflow → Coordination | “Five highlight cards filed with source evidence.” |
| Audit → Identity | “Four pass; one claim has no current source date.” |
| Identity → Adaptation | “Goal not reached. Replace or verify the unsupported card.” |

The user sees only Identity’s useful summary in chat and can open Agent activity to inspect the exchange.

## 4. Product capability contract

### Capability

Run one stamped department as a visible, bounded, evidence-backed loop until its done-when condition holds or an explicit waiting, blocked, refused, failed, or stopped state is reached.

### Constraints

- Identity is the sole user-facing voice.
- Adaptation proposes but never applies its own proposal.
- Priority admits work but never starts a run.
- Root validates and registers; a J2 workflow does not enter the shared Library.
- Coordination owns order, slots, handoffs, and one-run-at-a-time execution.
- Audit checks; it does not convert findings into scores.
- A bargain is bounded by four hops, fifteen minutes, and its allowed spend.
- All runs and exchanges are visible as operational records.
- Every state transition is idempotent and attributable.
- J2 stops proposing when the stamped done-when condition holds.

### Non-goals

- Do not redesign J1 or infer a second department from a J2 message.
- Do not implement the source document’s unclear ninth journey.
- Do not publish a department-specific workflow into the shared Library.
- Do not expose private reasoning.
- Do not let a workflow, function, or tool speak directly to the user.
- Do not make Audit a score or leaderboard.
- Do not add multi-workflow parallel execution in this version.

## 5. The eight required steps

| Step | Required behavior | Exit evidence |
|---|---|---|
| 1 | Identity checks the Root-stamped goal, rules, and done-when. If insufficient, it asks one question at a time until its own start standard passes. | `identity.assessed` with `sufficient=true`, stamp revision, and evidence; or one open Identity ask. |
| 2 | Adaptation reads Identity. It uses the nearest suitable Library template when one exists; otherwise it shapes a department-owned workflow from the goal, rules, and available practices. It may propose 2–5 or more workflows; there is no fixed count. | Versioned proposal with source (`library` or `shaped`), workflow definitions, rationale, and expected evidence. |
| 3 | Priority evaluates the proposal against the envelope and present work. It grants, refuses, or counters. Adaptation accepts or revises. | Bounded exchange with hop count, elapsed time, spend, and terminal disposition. |
| 4 | If the bargain cannot close, Identity rules from the goal and rules. If it cannot rule, Identity creates one user ask and waits. | Identity ruling with cited rule, or a single pending ask connected to the exchange. |
| 5 | Root validates the granted workflow against Sutra standards and registers it on the department record. A failed check returns reasons to Adaptation. | Immutable validation result plus department-local workflow version; no shared-Library write. |
| 6 | Coordination assigns the next slot. The workflow runs step by step and files its output and evidence. The envelope is enforced during the run. | Run record, step records, envelope readings, filed artifact version, and terminal run status. |
| 7 | Audit samples and checks the filed work against Identity. It files a finding to Identity. | Finding with check, evidence, verdict, and affected artifact/run references. |
| 8 | Identity evaluates Audit’s finding against done-when. If done, it informs the user and closes the loop. Otherwise Adaptation receives the remaining gap and returns to step 2. | `goal.reached` with evidence or a new cycle linked causally to the finding. |

## 6. Required sub-journeys

### J2.a — Is the identity good enough?

Identity’s start standard is machine-checkable:

- a non-empty goal;
- at least one done-when statement that can be checked from evidence;
- rules have explicit `go`, `ask`, `refuse`, or `always` behavior;
- no unresolved contradiction among the goal, done-when, and rules;
- the department knows where work and evidence will be filed.

If only the user can supply a missing fact, Identity asks one question. It preserves previous answers and re-evaluates after each answer. `Just do it` may accept explicitly recorded assumptions only when no `ask` or `refuse` rule is violated.

### J2.b — Decide what to do next

Adaptation follows this order:

1. Search the applicable Library templates using the Identity goal, required output, evidence, and constraints.
2. Use the nearest valid template if it satisfies all hard constraints.
3. If no template fits, shape a department-local workflow from Identity and available practices.
4. File the proposal. Never execute it directly.

Template similarity never overrides a hard rule. “No template” is not itself a user-facing blocker.

### J2.c — The bargain

Priority returns exactly one of `grant`, `refuse`, or `counter`. A counter names the violated envelope dimension and a concrete admissible change. Adaptation can accept or issue a new proposal. The thread ends at four hops, fifteen minutes, spend exhaustion, or agreement.

### J2.d — Close a conflict

At a bound or semantic conflict, Identity applies the stamped goal and rules. It must not invent a new policy. If no existing rule decides the conflict, Identity asks the user once and waits without starting the disputed work.

### J2.e — Root’s check

Root validates structure, capability availability, authority, safety, evidence requirements, envelope compatibility, and idempotency. A refusal is structured and goes back to Adaptation. A pass registers a new immutable workflow version on the department record.

### J2.f — Run the work

Coordination selects one admitted workflow, assigns one idempotent slot, and wakes only the assigned workflow. The workflow records each step, files outputs through the record layer, and returns status to Coordination. Retries reuse the logical slot and cannot duplicate an external effect.

### J2.g — Read the result

Audit performs a direct evidence check against Identity. Identity routes the finding:

- missing fact known only by the user → question to user;
- change requiring user consent → ask to user;
- correctable gap → Adaptation;
- done-when proven → completion evaluation.

### J2.h — Next move or done

Adaptation receives a precise remaining gap, not a generic failure. It can pursue, learn, crystallize, or grow through another proposal. Only Identity can declare the goal reached, and only from Audit evidence that satisfies done-when.

## 7. Required edge behavior

| Edge | Required product behavior | User-visible result |
|---|---|---|
| J2.1 Identity insufficient | Ask one question at a time; re-check after every answer; never start early. | Identity says what is missing and waits. |
| J2.2 Bargain bound reached | Close the bargain and escalate its complete record to Identity. | Identity rules or asks; the work is not silently refused. |
| J2.3 Identity cannot rule | Create one deduplicated, answerable ask. | User sees the decision, options or needed fact, and consequence of no answer. |
| J2.4 Root refuses workflow | Return structured reasons and constraints to Adaptation for reshaping. | Identity reports that the plan is being reshaped; no failed workflow is registered. |
| J2.5 Envelope exceeded | Hold the workflow before the next charge or call; preserve resumable state; escalate according to the rule. | Identity reports the exact limit, consumed amount, and permitted next action. |
| J2.6 External send requested | Apply the stamped rule. Ask only when the rule says ask; refuse when it says refuse; proceed when it says go/always. | Identity owns any necessary consent. |
| J2.7 Result fails check | Return the gap for at most two repair attempts; after the bound, Identity reports the unresolved failure. | User can see attempts and evidence in Agent activity. |
| J2.8 Goal changes | Freeze new admissions, preserve in-flight evidence safely, and route the change through Root for a new Identity stamp before resuming. | Identity shows the old and new revision and whether running work was completed, stopped, or superseded. |

### Operational safeguards not named as J2 journeys in the source

These are necessary for a testable product but do not create new canonical J2 labels:

- **Missing capability:** Root refuses registration or Coordination blocks before a run, with the missing capability, why it is needed, and recovery options. Adaptation can reshape around an available capability. Identity asks the user only if a stamped rule requires a choice or authority.
- **Tool or model unavailable:** Retry only within the workflow policy; then block with resumable state.
- **Crash or restart:** Recover from the append-only event record; do not duplicate admitted work or external effects.
- **Duplicate event:** Ignore by idempotency key and retain an audit entry.
- **Stale proposal or stamp:** Refuse work whose Identity revision is not current.
- **Malformed or unsafe output:** Do not file as a successful artifact; record the check and route the gap.
- **User stop:** Stop new admissions immediately, ask running work to halt safely, record final state, and let Identity confirm what stopped.
- **No progress loop:** Detect repeated equivalent proposals or findings and escalate to Identity instead of looping forever.

## 8. Canonical J2 event contract

The event ledger is the one authoritative boundary shared by runtime, API, UI, tests, and fixtures. Projections such as chat and Agent activity are derived from it.

```json
{
  "schema_version": "j2.event.v1",
  "event_id": "evt_...",
  "idempotency_key": "department/cycle/step/attempt/action",
  "department_ref": "dref-...",
  "identity_revision": 3,
  "cycle_id": "cycle_...",
  "step": 3,
  "journey": "J2.c",
  "actor": "Priority",
  "recipient": "Adaptation",
  "action": "proposal.countered",
  "state": "waiting",
  "summary": "Reduce sources from five to two to fit today's call limit.",
  "reason_codes": ["envelope.calls"],
  "rule_refs": ["rule-2"],
  "proposal_ref": "proposal_...",
  "workflow_ref": null,
  "run_ref": null,
  "causation_id": "evt_...",
  "correlation_id": "cycle_...",
  "evidence_refs": [],
  "envelope": {"calls_used": 2, "calls_limit": 4, "money_used": 0.02, "money_limit": 0.05},
  "occurred_at": "2026-10-06T10:00:00Z",
  "visibility": ["agent_activity"]
}
```

### Allowed actors

`Root`, `Identity`, `Adaptation`, `Priority`, `Coordination`, `Audit`, a registered workflow engine, and `User`.

### Required event families

- `identity.assessed`, `identity.questioned`, `identity.ruled`, `goal.reached`, `goal.revised`
- `proposal.created`, `proposal.countered`, `proposal.accepted`, `proposal.granted`, `proposal.refused`
- `workflow.validated`, `workflow.registered`, `workflow.blocked`
- `slot.assigned`, `run.started`, `run.step_recorded`, `artifact.filed`, `run.completed`, `run.failed`, `run.stopped`
- `audit.started`, `audit.finding_filed`
- `ask.created`, `ask.answered`
- `envelope.held`, `capability.missing`, `cycle.stalled`

### API expectations

- `GET /api/departments/{ref}/j2` returns current cycle, step, state, open ask, done-when status, and projection cursor.
- `GET /api/departments/{ref}/j2/events?after={cursor}` returns ordered, department-scoped events.
- `POST /api/departments/{ref}/j2/start` is idempotent and valid only after J1 readiness.
- `POST /api/departments/{ref}/asks/{ask_id}/answer` accepts an answer exactly once.
- `POST /api/departments/{ref}/j2/stop` stops new admissions and starts safe cancellation.
- Errors use stable codes: `IDENTITY_INSUFFICIENT`, `STALE_IDENTITY`, `BARGAIN_BOUND`, `ROOT_REFUSED`, `ENVELOPE_HELD`, `CAPABILITY_MISSING`, `EXTERNAL_AUTH_REQUIRED`, `CHECK_FAILED`, `CYCLE_STALLED`, `ALREADY_HANDLED`.

## 9. Functional requirements

### Runtime

- FR-1: J2 starts only from a valid `j2_ready` handoff with a current Root stamp.
- FR-2: Persist every transition before waking the next actor.
- FR-3: Enforce actor authority at the boundary; an actor cannot perform another function’s action.
- FR-4: Enforce bargain bounds and escalate instead of silently refusing.
- FR-5: Register workflows only on the department record.
- FR-6: Enforce one active workflow run per department in this version.
- FR-7: Enforce envelope limits before spending.
- FR-8: Require evidence for Root validation, Audit findings, and goal completion.
- FR-9: Resume safely after restart from the event ledger.
- FR-10: Detect stale Identity revisions, duplicate events, and no-progress cycles.

### User experience

- FR-11: Show the J2 phase and plain-language state on the department screen.
- FR-12: Keep user conversation in Identity chat only.
- FR-13: Provide Agent activity with live updates, actor filters, cycle grouping, expandable event details, and evidence links.
- FR-14: Show bounds visibly during bargains and runs.
- FR-15: Show one clear action for a pending ask and prevent double answers.
- FR-16: Provide a visible Stop control and show its outcome.
- FR-17: On completion, show the satisfied done-when clauses and supporting Audit evidence.
- FR-18: On block or failure, show the responsible function, exact reason, preserved progress, and recovery path.

### Accessibility and safety

- FR-19: Activity state must not rely on color alone; all interactions work by keyboard and have accessible names.
- FR-20: Redact secrets and sensitive tool payloads before persistence or display.
- FR-21: Never display hidden reasoning. Display only structured decisions, cited rules, evidence, and concise summaries.
- FR-22: All endpoints and projections are strictly department-scoped.

## 11. Success measures

- 100% of J2 state transitions have one canonical event and a correlation chain.
- 0 duplicate registered workflows, runs, artifacts, external effects, or answered asks under replay tests.
- 100% of user-facing messages originate from Identity.
- 100% of completed goals link to Audit evidence for every done-when clause.
- Bargains never exceed four hops, fifteen minutes, or their spend.
- A tester can identify the current actor, current step, latest decision, and next expected action within ten seconds.
- All UAT scenarios and automated unit, contract, integration, browser, accessibility, restart, and security tests pass.

## 14. Rollout

1. Keep J2 behind a feature flag.
2. Enable it only for an isolated demo department with deterministic adapters.
3. Run the scripted user journeys while Agent activity is visible.
4. Enable for local real capabilities after contract and failure tests pass.
5. Preserve an immediate off switch. Turning J2 off must stop new admissions without corrupting an active cycle.

## 15. Open decisions for review

1. **Identity sufficiency:** Are the five checks in J2.a the desired first standard, especially the requirement for machine-checkable done-when evidence?
2. **Goal change:** Confirm that J2.8 must always return through Root for a new stamp. This PRD recommends yes.
3. **External send:** Confirm that the stamped rule is the only authority and that there is no unconditional first-time ask. This follows the source’s “ask only when a rule says ask.”
4. **Missing capability label:** Should the source add this as J2.i/J2.j, or keep it as an operational safeguard without a journey label?
5. **Repair bound:** The source says two send-backs today. Confirm two remains the product rule.
6. **Agent activity detail:** Confirm that concise decisions, rules, inputs/outputs, and evidence are sufficient; hidden model reasoning will never be shown.
