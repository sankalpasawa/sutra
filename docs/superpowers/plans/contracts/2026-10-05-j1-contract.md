# J1 contract snapshot — 2026-10-05

Source: https://sankalpasawa.github.io/asawa-site/native/system/department.html#j1

This branch implements the published J1 journey only. The UI name remains
`Root`. Earlier J1 PRD/code and commit `3ed3c400` are excluded.

## Happy path

| ID | Required behavior |
|---|---|
| J1-S1 | The user names the organisation, optionally supplies first words, and presses Found. |
| J1-S2 | Root appears as the organisation helper. |
| J1-S3 | Setup asks one question at a time until the department is clear. `just do it` stops clarification. |
| J1-S4 | Each answer is the next version of the same Request conversation. |
| J1-S5 | Setup selects a name, purpose, and versioned Library template or the explicit organic route. Birth is automatic unless an effective `ask` rule matches. |
| J1-S6 | Setup creates one department with Identity, Priority, Coordination, Adaptation, and Audit, then hands it the complete ordered conversation as goal context. |
| J1-S7 | Root tells the department name, born engines, and first action; the child appears once. J1 emits `j2_ready` but does not perform J2 work. |

## Edge paths

| ID | Required behavior |
|---|---|
| J1.1 | Vague answers produce one new question per turn until clear or `just do it`. |
| J1.2 | `just do it` uses and discloses safe template defaults; required data without a safe default is asked for. |
| J1.3 | A compatible existing child is reused; an incompatible collision receives a distinct name. |
| J1.4 | No fitting template selects organic, with no born work engines and Adaptation queued. |
| J1.5 | A request for two departments creates only the first and leaves the second as an inert suggestion. |
| J1.6 | A matching inherited `ask` rule freezes the selected revision and waits; decisions are durable and idempotent. |
| J1.7 | No answer after the existing 60-second front bound leaves the Request waiting and creates no child. |
| J1.8 | Model unavailability uses the existing 30/120/600 retry schedule, retains the Request, and tells the user after final failure. |
| J1.9 | Reload restores the conversation and reconciles an interrupted founding operation without duplicates. |

## Durable boundaries

Request messages have stable IDs, actor roles, text, and order. A founding
operation is identified by Request ID plus selected revision and checkpoints:
Root, child, functions, rules/limits, goal context, born engines, `j2_ready`,
and final tell. Reconciliation completes missing projections and never creates
around contradictory state.
