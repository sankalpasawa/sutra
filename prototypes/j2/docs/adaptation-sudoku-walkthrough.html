Common start

Identity turns four words into a charter

"Build me a Sudoku site" names no documents, so the run builds the website directly (no PRD → HLD → LLD chain). Identity finds the brief too thin and asks the Requester 1–4 questions (in the saved run: difficulty levels, which helper features, and live hosting). From the answers it writes the charter. Code checks the charter: at least 3 checkable done-when items, every fact traced to the brief, and any item dropped from the brief put back to the Requester.

#Done-when item (real, from the saved run)
1One HTML file, inline CSS and JS, no build step
2A 9×9 grid; select a cell, enter or clear 1–9
3New Game with Easy, Medium, Hard; puzzles generated in the browser
4A solver counts solutions; only one-solution puzzles are accepted
5Duplicates in a row, column or box are highlighted
6Pencil-note mode; entering a number updates that cell's notes
7Undo, one step at a time, including note changes
8Hint fills one correct cell; Check marks wrong entries
9A running timer that stops on completion
10A completion message when the grid is correctly filled
11No localStorage, sessionStorage, cookies or IndexedDB
12Numbered Vercel deploy steps and a marked placeholder for the live URL
13Usable at 360px wide and on desktop

The charter's rules also say: "Do not add persistence or features beyond the chosen scope without a new Identity ruling." That rule matters for depth (section 4). Both flows start from this charter. Identity is the same in both.

Version 1 · how it runs in the repo today

Adaptation proposes the smallest workflows that close the gap

  1. J2.bAdaptation

    Reads team.md and adaptation.md, the run state (budget 100, the rate card, item minimums) and its task. The task says, in this order:

    • "Propose the smallest workflows that close the gap"
    • Each workflow lists the done-when items it covers
    • No check or report workflows
    • Exactly one work atom per workflow, with its checks
    • What doesn't fit the budget goes in left_out

    How to split the work is the LLM's own choice. In practice it splits by screen or section: Tap Rush got one workflow per screen.

    Predicted plan for the Sudoku charter:

    W-2 Puzzle generator and solver3, 41interactive_feature
    W-3 Notes and undo6, 71interactive_feature ×2
    W-4 Hint, check, timer, completion8, 9, 101interactive_feature ×2
    W-5 Deploy steps121page_section
    W-6 Single file, no storage1, 111styling
  2. J2.b codeValidator

    Checks the reply has its fields and each atom has checks. A plan check uses the website conditions; only N8 (nav) has one. Anything that fails is re-asked once, then dropped or patched by code. Nothing in this step asks whether the plan is enough.

  3. J2.c–dPriority

    Prices each workflow from the rate card (interactive_feature 10, page_section 10, styling 5, plus item minimums). It replies GRANT, COUNTER or REFUSE. With budget 100 and roughly 8–10 interactive parts, this plan is close to the limit, so a COUNTER, or items moved to left_out, is likely. There are up to 4 bargaining exchanges; then Identity decides.

  4. J2.e–fCoordination + builders

    Each registered workflow becomes a "W-n Builder". It builds its section in one atom, with up to 3 attempts against that atom's checks. The puzzle generator gets the same single atom as the deploy-steps text.

  5. J2.gAudit

    LLM findings, plus code checks of conditions N1–N8: the page parses, no JS errors, no overflow at 360/1280px, links work, facts present, nothing invented, forms work, nav reaches every section. This is the first point where anything judges whether the plan was good, and it is after the build.

  6. J2.hIdentity

    Code decides whether the result is workable. If it is, the run is done. If not, the open items go back to Adaptation for a new cycle. Limits: 6 cycles, 30+ turns per cycle, and a stop when the same failure repeats twice. The run ends as Done, Done with open items, or Paused for the Requester.

Version 2 · realization and certainty as axes, with a confidence judge

Adaptation cuts by kind of thinking, reads certainty, and the judge scores before anything is built

  1. Step 1Factors

    Adaptation first lists what makes a Sudoku site good or bad.

    • From the brief (quoted): three difficulty levels; a unique solution; notes, undo, hint, check and timer; no storage; phone and desktop; deploy steps.
    • General (what makes Sudoku sites succeed):
      • Puzzles feel right for their level. Hard must be harder than Easy, not just emptier.
      • Fast number entry on a phone (an on-screen pad, not the keyboard).
      • Keyboard entry on desktop.
      • A new puzzle appears quickly on a mid-range phone.
      • Errors are shown without giving away the answer.
    • Budget: 100 credits and 6 cycles.

  5. J2.c onwardSame as today

    Priority funds what passed; Coordination orders it (decisions before builds, by inputs_from); builders, Audit and Identity work as before. The difference: Audit should find fewer surprises, because the gaps it would have found (undo over notes, a uniqueness that was never proved, a cramped phone layout) were closed before building.

Where this clashes with today's code (fix in the code step)
  • The validator rejects a workflow that covers no item and fixes nothing (_underpriced). D-1 to D-4 deliver nothing, so they would be refused. A workflow that only informs items needs to count.
  • The rate card has no part for decision work. There is nothing to price D-1 to D-4 with.
  • Builders see only their own section (J2_SLIM). D-2's layout and D-4's state model must reach B-1 to B-4 through inputs_from.
  • On the Anthropic API path, Adaptation's reply is capped at 900 tokens. Factors, stages and 9 workflows will be cut off; the cap must rise.
  • 9 workflows instead of 6 costs more. Budget 100 may not cover it, and some items would move to left_out.
4 · How deep each flow goes

Thinking depth versus feature depth

Two kinds of depth are mixed up easily. Feature depth is how many things the site does. Thinking depth is how well each thing is worked out before it is built. Today, feature depth is fixed by Identity's done-when list, and Adaptation is told not to add scope. The new flow goes deeper in thinking. It does not add features by itself.

5 · Test prompts

How to compare the two flows

Use two prompts. The first is your exact brief: it tests how far each flow fills in a thin request. The second fixes every fact, so the only difference between runs is Adaptation.

Prompt A: the open brief

Build me a Sudoku site.

Give Identity the same answers in both flows. Paste these when it asks:

Difficulty: Easy, Medium and Hard.
Helpers: pencil notes, undo, hint, check, and a timer.
Saving: no saved games, no browser storage.
Hosting: give me the steps to put it on my own Vercel account; don't publish it yourself.
Devices: phone and desktop.
Anything else: you decide, and tell me what you assumed.

Prompt B: the controlled brief

Build a Sudoku game as one web page.

Players: anyone on a phone or laptop, no login.
How it plays: a 9x9 grid. The player selects a cell and enters or clears a number 1 to 9. New Game offers Easy, Medium and Hard. Puzzles are generated in the browser and each one has exactly one solution.
Helpers: pencil-note mode, Undo (one step at a time, including notes), Hint (fills one correct cell), Check (marks wrong entries), a timer that stops when the puzzle is solved, and a message when it is solved.
Mistakes: numbers that clash in a row, column or 3x3 box are highlighted.
Look: clean and calm, works on a 360px-wide phone with no horizontal scrolling.
Rules for the build: one HTML file with inline CSS and JavaScript, no build step, no external images or fonts, no browser storage of any kind, no sign-up, no ads.
Deploy: include numbered steps for putting the file on the player's own Vercel account and a marked placeholder for the live URL. Do not publish it.
Anything not listed here is not decided. Ask me, or mark it to be confirmed. Do not invent it.

How to run it

  • Same settings in both flows: the same model; J2_MEMORY=0 (no lessons or playbooks from earlier runs); J2_DELAY=0; J2_BUDGET=100; and the same Identity answers.
  • Original flow: the repo as it is today.
  • New flow: first as a planning-only pilot (plan + judge, no build), which compares plans. Then, once wired in, a switch such as J2_REALIZATION=1 compares built sites.
  • How many runs: 3 per flow per prompt, in alternating order (orig, new, new, orig, …).
