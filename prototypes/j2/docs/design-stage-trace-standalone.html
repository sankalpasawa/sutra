J2 · Realization + certainty · one real run, traced · 25 Oct 2026

How the design department was born, judged, split and built in one real J2 run

Run tax-realization / j2-20261025-003747. Brief: a tax set-aside calculator for freelancers in India. Every name, number and quote below comes from the run's own files: realization.json, decisions.md, atoms.json, chat.jsonl and the final page site/v9.html.

The answer first

  1. Realization made the design department. It found 3 design factors in the charter (plain words, Indian rupee format, fit at 360px and 1280px) and gave them to a "design" stage.
  2. Certainty set how the department must work. The five gates gave the zone "analyze": compare options, choose one, then build. So design became a decide workflow, not a build workflow.
  3. The judge joined the two axes. It failed the design workflow two times. First on a certainty question (no options were compared). Then on a realization question (it mixed two kinds of thinking). Adaptation fixed the first and split the workflow in two for the second.
  4. The two design decisions reached every builder. The final page uses the exact words, the 2/4-column grid, the 640px switch and the rupee format that the decisions set.
  5. Two gaps. The gate held all build work, but Adaptation built it anyway. Builders used their own element ids, not the ids in the decisions.

Where the two axes join

Realization and certainty write one plan together. The judge then asks questions from both axes. Code adds up one score. A low score sends a fix back, labelled with the axis that must change.

Certainty: the five gates

Adaptation · certaintyCode checks the rule
InThe charter and the factors
DoesAnswers 5 signals with yes, no or unknown, and quotes the evidence. A fixed rule turns the answers into a zone. Code checks that the zone follows the rule.
OutZone analyze for the plan
Gate 1 · broken

Is something broken now, with no clear cause?

Yes → stabilize (repair only)

Answer: no

"Nothing is built yet and there are no open findings."

Gate 2 · reaction

Does success depend on how people react?

Yes → experiment (1 to 3 small tests)

Answer: no

"The brief asks for a working calculator, not a result that depends on how people react."

Gate 3 · facts given

Are all the facts given?

Needed "yes" for operate

Answer: unknown

"It does not give the tax slabs, rebate or financial year, and with no web access they come from memory and are unverified."

Gate 4 · known pattern

Does a known pattern turn the facts into the output?

Needed "yes" for operate

Answer: yes

"A single-file form with number inputs, a calculate button and a result block is a standard pattern."

Gate 5 · open choices

Are there several valid ways, where a wrong pick costs?

Needed "no" for operate

Answer: yes

"Several valid ways to compute a monthly set-aside … There are also several ways to lay out 12 month fields on a 360px screen. A wrong pick gives misleading numbers or a cramped page."

Rule result

Not broken, no reaction → not stabilize, not experiment. Facts unknown and open choices yes → not operate. So: analyze.

Second rule: 2 or more "unknown" answers move the zone one step toward less certain. Here only 1 is unknown, so the zone stays analyze. Code ran the same rule and agreed.

ZoneWhenShape a workflow must have
operateFacts given, known pattern, no open choicesBuild directly
analyzeOpen choices or missing factsCompare options, choose one, give the reason, then build
experimentSuccess depends on reactions1–3 probes, each with hypothesis, signal, fails-if, limit
stabilizeBroken, cause unknownRepair only, add nothing
Design thread

Gate 5 names the design question: how to lay out 12 month fields on a 360px screen. So the design stage gets zone analyze: it must compare layouts and choose one before anyone builds.

Certainty also sets one zone per workflow. All 4 thinking workflows (compliance, product, design, engineering) are analyze or operate by their own open choices. All 4 build workflows are operate, because the decisions close the choices before they start.

Decision · Layout and amount format

Question: How is the page laid out so it fits 360px and 1280px, and how are rupee amounts written?

OptionForAgainst
A: one column, 12 fields stackedSimplest, no overflow riskPhone users scroll past 12 fields to the button
B: grid, 2 cols < 640px, 4 cols ≥ 640px, ≤ 960px ✔6 rows on phone, 3 on desktop; ~158px per cell at 360pxHint may wrap; 640px is untested at other widths
C: table, one row per monthCompactCramped at 360px; shows results before input
Intl en-IN, whole rupees ✔Gives ₹12,50,000 directlyDepends on browser locale data

Could fail if: a long number widens a cell; the rates table overflows at 360px; a browser prints 1,250,000; large phone text crowds 2 columns; it breaks between 640px and 700px.

Rules for builders (8): CSS grid with 2 minmax(0,1fr) columns, 4 inside @media (min-width:640px) · page max-width 960px, border-box · no scroll wider than the window at 360/1280, also after 12 × ₹99,99,999 · inputs and button ≥ 16px font and ≥ 44px tall, no fixed width over 320px · months in DOM order April→March · every amount through formatInr() (1250000 → ₹12,50,000, 109200 → ₹1,09,200, 0 → ₹0) · tables width 100%, cells wrap · focus outline ≥ 2px.

The same department in base J2, for contrast

Base J2 has no factors, stages, gates or judge. Adaptation grouped charter items into 4 build workflows in one call.

Base J2
  • Design was part of one build workflow: W-2 "Page header, navigation and styling". Steps: "Add CSS … mobile-first, box-sizing border-box, max-width 100%."
  • No layout options, no fixed word list, no amount-format rule.
  • A layout problem showed up at Audit: "the twelve month boxes sit above the calculate button on a phone". It took a fix workflow (W-7) to make the boxes collapsible.
  • 12 workflows, 4 fix rounds, 168 credits. 0 of 7 correct amounts.
Realization + certainty
  • Design was its own stage with 3 owned factors, and two decide workflows that closed before any build.
  • 3 layouts compared, one chosen, 8 builder rules and a fixed word list.
  • Audit found one placement problem and no layout or wording problem.
  • 9 workflows, 3 fix rounds, 126 credits. 7 of 7 correct amounts.

The two charters differ a little. Base asked for an expenses field and optional month fields. This is one run of each.

What this run shows, and what to fix

Works

  • Realization found the design need in the charter and gave it an owner.
  • Certainty forced a comparison of layouts before any build.
  • The judge caught one certainty fault and one realization fault in the same workflow, and each fix used the matching axis.
  • Builders followed the design words and layout closely.

To fix

  1. Enforce the gate. Held work was built anyway.
  2. Route world facts to a question early. The tax gap was "research:", so no question went out until Audit.
  3. Turn builder rules into atom checks. Ids and the 640px switch were not tested by code.
  4. Steady the judge. "Tax rules and wording" fell from 0.95 to 0.70 with no change.
