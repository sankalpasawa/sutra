# ADR-042 — Artifact fields: kind, facing and doc layer (PROPOSED under D74)

**Status**: Proposed · **updated**: 2026-09-11 · author: CEO of Asawa

## Status

Proposed — 2026-09-11. Awaiting the founder's ruling recorded in D74 ("Proposals still awaiting ruling: artifact fields kind/facing/doc layer"). Nothing in the engine changes until accepted; the fields already exist on paper in `holding/directory/artifacts.jsonl` and `ARTIFACTS.md`, produced by `holding/directory/census.py`.

## Context

D74 fixed the vocabulary of record: Domain (department), Charter, Placement, Artifact; inside Artifact: Module, Component, doc layer. It also closed the vocabulary: every output fits these dimensions, and a genuinely new kind is surfaced to the founder rather than added silently (`hooks/creation-guard.sh`, plugin 2.264.0).

"Artifact" by itself is too coarse to answer the questions the desktop and the guard ask: is this thing something a user opens, something an operator runs, or plumbing; is it a document and at which layer; what is it, in one word. The Directory Program applied three fields to every artifact it found and the census shows they carry the whole estate without an `other` bucket.

Census of 2026-09-11 (repo artifacts, `holding/directory/summary.json`):

| Field | Values in use | Rows |
|---|---|---|
| kind | ledger 1,412 · doc 1,165 · code 511 · page 508 · test 475 · policy 180 · plan 157 · hook 143 · cli 103 · adr 81 · skill 33 · charter 26 · engine 14 · app 7 · direction 1 · protocol 1 · sql 1 | 4,818 |
| facing | backend 4,167 · user 515 · operator 136 | 4,818 |
| doc layer | none 2,834 · L8 800 · L14 514 · L13 338 · L7 132 · L10 81 · L9 55 · L6 39 · L12 18 · L11 6 · L5 1 | 4,818 |

Canon artifacts (13) and modules (5) carry the same three fields.

### Alternatives considered

- **Surface as the container**: rejected by the founder ("we are not using surface"). Artifact is the container; facing carries what surface tried to say.
- **Free-text type per artifact**: no closed list, so the creation guard cannot tell new from known, and the desktop cannot group. Rejected.
- **Kind only, no facing or layer**: kind answers "what is it" but not "who touches it" or "where does it sit in the documentation stack"; the Org > Apps and Docs views need both. Rejected.
- **App as a top-level kind for everything user-facing**: the founder's word "app" names Modules for users (PROPOSED in D74); it is one kind value here, not a replacement for facing.

## Decision (proposed)

Every Artifact record carries three fields, all from closed lists:

| Field | Closed list | Rule of derivation (census.py) |
|---|---|---|
| kind | ledger, doc, code, page, test, policy, plan, hook, cli, adr, skill, charter, engine, app, direction, protocol, sql | `kind_v4()`: path and name rules, one value per artifact, no `other` |
| facing | user, operator, backend | `facing()`: user for pages, apps and modules shown in the desktop; operator for CLIs, commands, skills and hooks an operator invokes; backend for everything else |
| doc layer | L5 to L14, or none | `doc_layer()`: from the LLM-first documentation stack; none for artifacts that are not documents |

Rules that follow:

1. A path that fits no `kind` is a NEW KIND event: surfaced to the founder and routed through `holding/NEW-THING-PROTOCOL.md` section 2a, never a silent addition (D74 rule 4).
2. Adding a value to any list is a canon change: this ADR is amended, the census rule is updated, and `check.py other` must still pass at 0.
3. Module and Component stay sub-structures inside Artifact (ADR-023 four-test for Module); they do not replace these fields.
4. The desktop reads the fields from the export (`holding/directory/export/org.json`, artifacts collection) until the engine stores them; the engine schema does not change under this ADR.

## Consequences

- The creation guard has a closed list to check against (already shipped in WARN mode; promotion to hard is a founder decision).
- The Directory papers (`ARTIFACTS.md`, `DOC-LAYERS.md`, `COMPONENTS.md`) become the reference for the lists, regenerated by `paper.py`.
- Open for the founder: whether `page` and `app` should merge under `app`; whether `ledger` (1,412 rows, mostly state and logs) should split into state and log.
