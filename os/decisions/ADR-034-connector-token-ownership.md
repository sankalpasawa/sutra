# ADR-034: Connector Token Ownership — the Connector Service is the only confidential client

**Status**: Proposed (founder direction 2026-08-20; stack fork resolved in-session — hybrid local-now/backend-shaped · GitHub App · Keychain-now/KMS-interface · architecture-before-implementation)
**Date**: 2026-08-20
**Supersedes**: the credential handling of the connector layer removed in `96edce8` (482 files; gmail-direct / slack-direct / composio adapter)
**Built against**: [B17 External Tools (Connector Layer)](../native/blocks/B17-external-tools-connectors.md) — DRAFT v1, parity SHA `f5d58e57…`. **Not edited by this ADR.**

## Context

The connector layer was deleted wholesale rather than refactored. The rewrite must answer, before any code, one question that is a one-way door: **which process holds the GitHub credential?**

Sutra today has no backend. It is an Electron shell over a local FastAPI process (`sutra-ui/app.py`, 127.0.0.1:7000) with 0600 JSON stores. The founder's brief assumed a cloud connector-service with Postgres and KMS. The resolved position is *hybrid*: build the interfaces the hosted version needs, back them locally today.

### Verified GitHub facts that constrain the answer

Every row fetched from docs.github.com on 2026-08-20. Several contradict widely-repeated older guidance.

| # | Fact | Source | Why it constrains us |
|---|---|---|---|
| F1 | GitHub **does** now support PKCE on `/login/oauth/authorize` — `code_challenge` + `code_challenge_method`, **`S256` only**, `plain` rejected | OAuth Apps & GitHub Apps authorization docs | The old "GitHub has no PKCE" advice is stale. PKCE is available to us. |
| F2 | `client_secret` is **Required** on `POST /login/oauth/access_token` for the web flow — **PKCE does not relax this** | GitHub App user-access-token doc, parameter table | PKCE on GitHub is defence-in-depth, *not* a public-client enabler. A desktop binary cannot complete the web flow without shipping a secret. |
| F3 | Device flow requires **no** `client_secret` | OAuth Apps authorizing doc | The only genuine public-client path GitHub offers. |
| F4 | Refresh requires `client_secret` **unless the token was generated by the device flow** | Refreshing user access tokens doc | **Keystone.** Device-flow tokens can be refreshed with no secret — so a secret-less client gets the *full* lifecycle, not a degraded one. |
| F5 | GitHub App user tokens: 8h lifetime, refresh token 6 months idle. Expiration is **on unless you opt out**; opting out removes `refresh_token` entirely | User access token doc | We keep expiration ON. Opting out to dodge refresh would trade a 8h credential for an immortal one. |
| F6 | Installation access tokens require a **JWT signed with the app's RSA private key**; 1h lifetime | Installation access token doc | The private key can never ship in the desktop bundle. **Installation tokens are structurally impossible in local-only mode.** |
| F7 | GitHub Apps expose fine-grained per-repository, per-resource permissions and require org-owner approval to install | GitHub Apps docs | Maps 1:1 onto the capability model. OAuth App `repo` scope does not. |

## Decision

**Option D, instantiated locally: the Connector Service owns the entire OAuth lifecycle and is the only component that ever holds a GitHub credential. Today that service runs on loopback inside the app bundle. The hosted deployment is the same service behind the same interface.**

Concretely:

```
Electron renderer  ──►  Connector API (loopback today, HTTPS later)  ──►  GitHub
   never holds a           owns: OAuth transaction, token exchange,
   GitHub token            refresh, CredentialStore, capability gate,
   ever                    tool gateway, audit sink
```

The renderer is treated as an **untrusted client of our own API**, not as a trusted part of the service. That is the single assumption that makes the local and hosted deployments the same architecture.

### Auth strategy is a swappable interface, not a fixed flow

| Deployment | Flow | Callback | Secret on device | Refresh | Installation tokens |
|---|---|---|---|---|---|
| **Local (today)** | Device flow (F3) | **none — no redirect URI at all** | none, ever | works, secret-less (F4) | ✗ impossible (F6) |
| **Hosted (later)** | Auth Code + PKCE S256 (F1) | `https://api.sutra.…/oauth/github/callback` | none — secret is server-side | standard, confidential client | ✓ available |

Both implement one `AuthStrategy` port. Choosing device flow locally is not a workaround; it is the correct flow for a client that cannot hold a secret, and it deletes an entire attack surface (see below).

## Options considered

| | **A** Desktop owns token | **B** Backend owns token | **C** Desktop does OAuth, hands result to backend | **D** Connector Service owns whole lifecycle |
|---|---|---|---|---|
| Possible at all? | Only via device flow — web flow blocked by F2 | Yes | Only via device flow — F2 | Yes |
| **Security** | Token in the process that renders untrusted HTML | Strong | Weak — token transits the least trusted process | Strong |
| **Token exposure** | Full, permanent | Never leaves service | Full at least once; a leak at that moment is undetectable | Never leaves service |
| **Desktop compromise** | Total loss: attacker gets a 6-month GitHub grant | Loss bounded to the session; token unreachable | Total loss (same as A) | Loss bounded to the session |
| **Backend authorization** | None possible — service never sees the calls | Enforceable | Enforceable, but bypassable: desktop can call GitHub directly | Enforceable, and **unbypassable** |
| **Multi-device** | Re-auth per device | Native | Re-auth per device | Native |
| **Revocation** | Best-effort; a stolen token keeps working | Instant and complete | Best-effort | Instant and complete |
| **Auditability** | Client-authored logs = unfalsifiable claims, not evidence | Service-side, tamper-evident | Client can act off-log | Service-side, tamper-evident |
| **Agent execution** | Agent must run in the client | Agent runs anywhere | Split-brain | Agent runs anywhere |
| **Background jobs** | Only while app is open | Yes | Only while app is open | Yes (hosted); local mode is honest about this limit |
| **Repository ops** | Uncontrolled | Gated | Gated but bypassable | Gated |
| **Token refresh** | Possible via F4, but 3 devices = 3 refresh races on one 6-month token | Single writer | Race-prone | Single writer |
| **Account switching** | Client-side state, easy to corrupt | Server-side, constrained by UNIQUE key | Client-side | Server-side |
| **Scalability** | N/A | Horizontal, stateless | N/A | Horizontal, stateless |

**A is possible but wrong.** F3 means a desktop app *can* obtain a token unaided. It should not. A token in the renderer's blast radius, with client-authored audit logs and no enforceable gate, converts "the agent may only read" into an honour-system claim. Every §37 guarantee ("permission decisions happen outside the model") collapses if permission decisions also happen inside the compromised client.

**C is the worst option, not a compromise.** The desktop still sees the token — so it carries A's exposure in full — while also paying for a backend. It buys storage centralisation and nothing else. Reject.

**B and D differ only in who runs the *authorization* leg.** D is chosen because splitting the OAuth transaction across a trust boundary is how state/PKCE binding gets broken in practice: whichever process generated the `code_verifier` must be the one that redeems it, and that process must also be the one that stores the result. Keeping the transaction whole in one owner removes a class of bug rather than mitigating it.

## Consequences

### Accepted

1. **No user-absent background GitHub work until the hosted adapter ships.** F6 is structural: no private key on the device means no installation token means no "agent opens a PR at 3am with nobody logged in." Local mode does user-to-server only. This is stated plainly in the UI rather than faked.
2. **Device-flow UX cost.** The user reads an 8-character code and types it at `github.com/login/device`. Worse than a redirect. Bought with: no redirect URI, no loopback listener, no custom scheme registration, and therefore no port-conflict, no scheme-hijacking by another installed app, no interception of an authorization code by a local process, and no callback endpoint to attack. For a desktop app this is a good trade.
3. **Loopback API must authenticate its own caller.** A local service holding GitHub credentials on 127.0.0.1 is reachable by every process on the machine. Mitigation is mandatory, not optional: per-launch bearer token in the app bundle's private dir, `Origin`/`Host` checks (the existing `TrustedHostMiddleware` DNS-rebinding defence extends here), and no `Access-Control-Allow-Origin: *`. Tracked as threat T-08.
4. **Credential migration local→hosted is a re-auth event, not a data migration.** We will not export Keychain material to a server. Users reconnect. This is the deliberate cost of not building a credential export path — the single most dangerous code path such a system could contain.

### Reversibility

| Choice | Door | Cost to reverse |
|---|---|---|
| `AuthStrategy` / `CredentialStore` / `ConnectorService` as ports | two-way | interface swap, no data change |
| GitHub **App** over OAuth App | one-way-ish | new app registration, every user re-installs and re-authorises |
| Credential **location** (Keychain vs KMS) | one-way | forced re-auth for every connector (accepted above) |
| Device flow vs web flow | two-way | both behind `AuthStrategy`; can run either per deployment |

### Revisit when

- Sutra ships a hosted control plane → enable the PKCE web-flow strategy and installation tokens.
- GitHub drops the `client_secret` requirement for PKCE web-flow exchanges (would make loopback+PKCE viable locally; would still not beat device flow on attack surface).
- A user needs GitHub Enterprise Server, where App availability differs → the fine-grained-PAT fallback path.
